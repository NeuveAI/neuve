# SDK capabilities

The [shape fixture recorder](src/smoke-fixture-recorder.ts) accepts `--record-fixture-root <absolute directory> --record-fixture <relative name>` only with either tools diagnose arm. The root and any relative subfolders must already exist. The name cannot contain absolute paths, empty segments, `.` or `..`. Every directory component from the filesystem root through the destination's parent is checked with `lstat`; symlinks and non-directories are refused. The destination must be new and is opened with `O_CREAT | O_EXCL | O_NOFOLLOW | O_WRONLY` at mode `0600`; a failed write removes only the file this call created. The recorder constructs frames from fixed tag, tool-name and Claude-model allowlists; keeps block indexes, stop reasons, numeric usage counters and error booleans; replaces identities and send stamps with stable placeholders; and empties all content and tool inputs. Unknown fields are dropped, and consumed accessors or capture errors refuse the whole write. The [offline round trip](tests/smoke-fixture-replay.test.ts) restores fresh identities and real adapter send stamps and compares production MCP tool events and usage.

The [recorded parallel-tool replay and logger regressions](tests/round-25c.test.ts) establish the current publication rules, superseding the handler-triggered publication descriptions below for streamed responses. A tool result leaves its response open until `message_stop`; later blocks use their own message id. A call's `tool.finished` follows its `tool.started`, may come before `message.finished`, and is never emitted for an unannounced call. Assistant-only replies retain handler-triggered publication. Frames after stream closure and output after an end-turn tool's turn ends still fault. Cumulative request usage is counted once, with only late corrections added to stream-derived totals. Every protocol-error exit first performs its transition, then schedules one contained warning, `claude-runtime protocol-error site=<code> frame=<type>[/<subtype or event.type>]`, in the session scope. Logger failures cannot replace the outcome or hold the state permit; fixed site codes and allowlisted SDK tags keep the line bounded.

A tool can run before its published response's stream closes. Until that response's first `message_stop`, root `content_block_stop`, `message_delta` and `message_stop` frames are accepted without publishing more output or tool calls, including during turn cleanup. Late usage replaces the response's cumulative counters and contributes only their difference to stream-derived turn totals; result-ledger totals already include the request and receive no second contribution. [Round-24 replay tests](tests/round-24.test.ts) compare both arrival orders, turn totals and the session ledger, and retain faults for added content, frames after stream closure and a new response after an end-turn tool.

Before any user-message offer succeeds, a child reopen keeps its original identity, including a fresh session's UUID or a fork's parent, point and chosen UUID. After a successful offer, every reopen resumes the current session at its latest point, even if no reply arrived. [The reopen tests](tests/round-22c.test.ts) cover these transitions through the production adapter. The full smoke reports `requestsStarted` from root SDK response ids and retry frames, and `requestsCompleted` from `message.finished` events, on both success and failure; [the fake entrypoint test](tests/smoke-entrypoint-16.test.ts) checks the totals without printing message text.

## Amended runtime contract

IPC validation remains strict for the fields consumed from `assistant`, `user`, `result`, `stream_event`, `system`, `rate_limit_event` and `conversation_reset`. Every other string tag, including undeclared `command_lifecycle` frames, is ignored before reply binding, message collection, usage accounting or turn-ending checks. Each ignored type is logged once per session through Effect, with only its tag. Tags outside `/^[a-z][a-z0-9_]{0,39}$/` become `unrecognized`. Ignored frames cannot advance a resume point or count as further output after an end-turn tool. [The round-20 production-adapter tests](tests/round-20.test.ts) compare normal and final events with and without lifecycle frames, and check tool endings, log privacy and malformed consumed frames.

If a child fault records a typed `TurnFailed` while a turn opens, waits for initialization or sends its first prompt, startup preserves that reason and waits for its `turn.finished` publication before returning the typed failure. A genuine SDK open failure or the 25-second open timeout without a recorded turn fault still returns `RuntimeUnavailable` with reason `start-failed`; the started turn retains its existing broken `provider-failed` ending. [The startup cases in the same tests](tests/round-20.test.ts) exercise open, initialization, frame delivery, first-send interruption and genuine launch failures without starting Claude Code.

`continuation(account)` returns the resolved absolute config folder, or `default`, with runtime kind `claude-code`. It reads no folder contents. The runtime declares `ownsLoop`, `toolEndsTurn`, `resumeInTurn`, `perMessageUsage`, `resume`, `fork`, `interrupt`, and `modelSwitchInSession`. `capabilities(account)` validates the account, then checks the configured path or `PATH` with `Bun.which` without starting a process or SDK query; a missing or non-executable file fails with `RuntimeUnavailable` reason `not-installed`, and `openSession` checks it again independently. The [capabilities tests](tests/capabilities.test.ts) cover configured absolute and relative paths, executable permissions, `PATH`, availability changes and registry propagation; [round-9.test.ts](tests/round-9.test.ts) exercises the public session entry points.

`openSession` maps `new` to a fresh `sessionId`. A `resume` maps to `resume`, optional `resumeSessionAt`, and `forkSession`. A fork also supplies a fresh `sessionId`, which [sdk.d.ts:2150-2154](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2150) permits, so `nativeSessionId` names the new session immediately after open. The session's getter and the registry wrapper follow the SDK init id and conversation resets. The SDK declares these identities at [sdk.d.ts:2146](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2146), [2154](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2154), [2162](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2162), and [1770](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L1770).

A public resume has no usage baseline. Its first result can include saved history in `modelUsage`, as [sdk.d.ts:5975](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L5975) and [6109](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L6109) describe. Until that first result, the adapter totals completed root requests from `message_start` and `message_delta`. Those figures also fill `message.finished.usage`. The first result establishes the cumulative baseline; later results use ledger differences, including internal requests. The first resumed segment therefore excludes internal requests absent from the root message stream. A backstop close also requires a fresh baseline, because it closes before a result ledger arrives. Subscription cost remains `null`.

Content arrays preserve text blocks and map each image to `{ type: 'image', source: { type: 'base64', media_type, data } }`. [sdk.d.ts:6578](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L6578) delegates user content to the Messages API. The installed `@anthropic-ai/sdk` 0.124.0 declares `Base64ImageSource` at `resources/messages/messages.d.ts:95-99` and `ImageBlockParam` at `:1811-1813`.

The message collector combines per-block assistant frames by API message id and takes request usage and stop reason from the stream. [sdk.d.ts:3709](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L3709) declares one assistant frame per completed content block, with the same message id across blocks and non-final block usage. [The partial-message declaration at sdk.d.ts:5767-5775](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L5767) lists `message_start`, content-block events, `message_delta`, and `message_stop`. Its general description says the complete assistant message follows the incremental events; the more specific per-block declaration explains why an assistant frame alone need not finish a response. Actual CLI ordering at message stop remains unverified live in this adapter. Publication occurs at `message_stop` using the last assistant block seen at that point. Without stream usage, the last assistant frame for the message supplies request usage.

`message.finished` emits once at the earliest of the root `message_stop`, the first Neuve handler invocation for that message, or result/turn completion. Stop and scope closure publish only responses already known complete; they drop unfinished responses without advancing the resume point. Handler invocation proves the model message has ended and publishes it before running the definition, so a coding-chat handler may wait on that event. With no stream stop reason, a tool invocation establishes `tool-use`. `resumePoint` is the latest root assistant chain UUID seen for that message at emission. Any later frame of that published response fails the turn with `TurnFailed` reason `protocol-error`. It emits no second or partial message event and never moves the published resume point. The live smoke settles whether Claude Code ever orders frames this way. [Round-9b tests](tests/round-9.test.ts) cover publication before results, handlers that wait for publication with and without streams, repeated handlers, and late frames.

A turn ending on a tool-result carrier with no trailing assistant message publishes that carrier's chain UUID as `turn.finished.resumePoint`. This includes end-turn tools and final structured output. The same UUID is the internal continuation point and the next child's `resumeSessionAt`. Post-turn query reopening and forks use that point, following [sdk.d.ts:2179-2186](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2179), so they keep the tool-result carrier rather than truncating at the assistant call. It does not overwrite `message.finished.resumePoint`. Result-envelope UUIDs are not transcript UUIDs. The public declarations do not expose a separate structured-output attachment frame or its chain UUID, so that final-output fork point remains unverified live.

`tool.started` fires when a completed tool call arrives in an assistant block or streamed content block. Every started call emits exactly one `tool.finished` before its turn finishes. A denied, cancelled, undispatched or unfinished call emits `errored: true`, including outstanding calls at a result or session close. Only calls whose handler started include `durationMs`. No finish event exists without a start event. The handler passes `{ callId, signal }` to the definition. The signal combines MCP cancellation with turn or session shutdown and a call-owned abort controller. A wait ending without an outcome aborts that signal before settling or replying to Claude Code. The id comes from the live-proven metadata or hook route; [sdk.d.ts:2827](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2827) declares the hook route.

In sessions with tools, `steerTurn` holds messages in the adapter until every Neuve tool call from the response has returned without `endTurn`. The response's tool calls come from its `tool_use` blocks, also listed in `message.finished.toolCalls`. The adapter offers held steers once, before returning the last tool result, whether handlers run in parallel or serially. Any end-turn handler discards held steers and increments the internal `discardedSteers` diagnostic, following ruling 6. This includes steers held between serial calls after an earlier call continued. A result without a tool handler offers held steers before completing the turn and waits for their result. Sessions without tools offer steers directly. [Round-10 tests](tests/round-10.test.ts) cover single handlers and no-tool responses. [Round-11 tests](tests/round-11.test.ts) cover parallel and serial calls through the runtime and in-memory MCP transport.

A handler's `endTurn: true` adds `_meta: { 'claude/endTurn': true }` to its MCP result, per [sdk.d.ts:2179-2183](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2179). The normal result completes the turn. Further root model output closes the query and still completes that turn; the next `startTurn` reports `protocol-error`. Both paths have fake coverage. Honouring this metadata in the installed CLI remains unverified live.

`setModel({ id, effort })` calls `query.setModel(id === "default" ? undefined : id)` then `applyFlagSettings({ effortLevel: effectiveEffort ?? null })`, declared at [sdk.d.ts:2988](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2988) and [3043](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L3043). Switches queue as whole operations. Each pair has a 25-second SDK deadline and saves only when both calls succeed on the same child generation. A failed pair retires the child with bounded disposal and keeps the previous saved selection for reopening. Reopened final queries retain the saved selection. A stopped session reports `session-stopped`. [Round-10 model tests](tests/round-10.test.ts) cover overlapping calls, failure, timeout, and generation replacement.

The coordinator's rulings 11, 18 and 19 define the public carrier point, waits and call completion. Handler waits have no runtime clock. They end on an outcome, call abort, turn end or session close. Permission waits end on the person's answer, the SDK signal or turn abort. The MCP per-call timeout remains 2147483647 ms. [Round-13 tests](tests/round-13.test.ts) advance Effect's TestClock by 66 minutes for both waits and cover abort ordering, call completion and live registry identity after fork init and conversation reset.


## Account models, effort and limits

The prompt-less status query uses `initializationResult().models`, declared at [sdk.d.ts:4783-4795](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L4783). This reuses the initialization response already needed for account status instead of adding another SDK method to the adapter. [The SDK's model-list method at sdk.d.ts:3105](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L3105) exposes the same initialized list. Neither path sends a prompt. The boundary maps `ModelInfo.value` to `RuntimeModel.id`, keeps only the contract fields, removes unknown effort levels, and drops malformed rows. An unavailable list leaves `models` absent without changing sign-in status. [Round-14 tests](tests/round-14.test.ts) exercise these paths with fake SDK children.

`ModelInfo` has no default flag in [sdk.d.ts:1442-1485](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L1442). The adapter places the row with `value: "default"` first and otherwise preserves SDK order. That row's identity as Claude Code's own default remains **unverified until the live smoke**. The smoke must compare the prompt-less query's model rows with Claude Code's picker for the same account folder, check that the picker default corresponds to `value: "default"`, and compare its resolved model with an unpinned session's reported model. The last check requires an authorized model request; this round ran only fakes.

An explicit `id: "default"` omits `Options.model` on open and uses `query.setModel(undefined)` in session. [The setModel declaration at sdk.d.ts:2984-2988](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2984) defines `undefined` as the default. Forks pass the parent's chain-entry UUID unchanged as `resumeSessionAt`; the fork's later points use their own chain UUIDs. [The session and resume declarations at sdk.d.ts:2150-2162](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L2150) distinguish a new session UUID from a retained chain-entry UUID. [The added round-14 cases in round-13.test.ts](tests/round-13.test.ts) cover a parent point reused on its fork, later fork points, and a last-frame tool carrier with multiple end-turn calls and discarded steers. This confirms adapter forwarding with fakes; it does not validate the CLI's transcript persistence live.

[EffortLevel at sdk.d.ts:723](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L723) includes `low`, `medium`, `high`, `xhigh`, and `max`. [Options.effort at sdk.d.ts:1974](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L1974) accepts that type, as does [applyFlagSettings.effortLevel at sdk.d.ts:3038-3045](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L3038). `max` is session-only and is never written to settings files. The SDK can reduce unsupported `max` to `high`; the adapter instead refuses an explicitly unavailable level with `TurnFailed` reason `protocol-error`, before any model-control call or turn prompt. That error carries only account and reason.

Each session learns its models from its own child's initialization result and replaces its list on later child initialization. An exact row id matches first, then `resolvedModel`. Without a known row or list, effort passes through. A row without `supportsEffort: true` suppresses effort; a supporting row with a declared levels list refuses levels absent from it. An absent effort clears an earlier session effort. [The reset semantics at sdk.d.ts:3025-3029](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L3025) say `effortLevel: null` restores the model's default effort, rather than restoring a query option or settings-file value; `undefined` has no effect. Before the first initialization there is no list, so open passes a supplied effort through. If that first list suppresses effort, the adapter clears it before any prompt. If it refuses the level, the turn fails before sending its message. Known non-effort rows omit effort when later children open. If a new child's list supports that requested effort again, initialization applies it before the next prompt.

Turn usage includes positive integer `contextWindow` and `maxOutputTokens` from that model's result ledger, declared at [sdk.d.ts:1503-1504](node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts#L1503). These fields stay outside `CallUsage`. The session retains each model's reported limits for usage emitted before later results; every later entry replaces that model's figures and omits missing or invalid values. No limits are supplied before a result reports them. [Round-14 usage tests](tests/round-14.test.ts) cover two independent models, later pre-result usage, invalid and missing figures, and the `CallUsage` boundary.

## Manual smoke

The [manual smoke entrypoint](src/smoke.ts) requires `--live` and an existing absolute Neuve state directory. It uses the default account and leaves the model unpinned throughout. Every turn has a three-response backstop. Each step reports `withinPlan` and fails if its completed-response count exceeds its plan. The whole run has a five-minute deadline and closes its sessions on completion or failure. Tests spawn this entrypoint with a preloaded fake and never import it.

Effect logs go to stderr through the smoke's logger. Stdout contains one JSON result line in every mode. A full-smoke failure reports `outcome: "failed"`, the active `step` (`probe`, `normalTurn`, `finalTurn`, `persistence`, `fork` or `tools`), `causeKind`, optional validated `errorTag` and contract `reason`, `expectedRequests: 8` and `wallMs`. It omits error messages, stacks and values. A successful full smoke reports only booleans and counts. `requests` counts `message.finished` events, while `expectedRequests` is 8. Observed counts exclude hidden retries and calls without those events. Each step has its own request count and `withinPlan` boolean: normal and final at most 2, completed inputs at most 3, fork at most 1, and tools at most 2. A steer folded into the first input request reduces completed inputs to 2 and the total to 7. The total `withinPlan` boolean fails above 8. These checks enforce the completed-response plan; SDK retries without a completed response remain outside this count. The second steer during `finish` adds no planned request. `successes` and `failures` count all boolean checks, treating a reported protocol error as failure. Any failed check sets a nonzero exit code. The existing `completed` and `failed` fields retain their count of the original four acceptance turns; the fork and tool outcomes have separate booleans. No token, message text, native id or model name is printed.

The [diagnose mode](src/smoke-diagnose.ts) separates resume from structured output within one request. Its steps run in order: `probe`, `freshFinal`, `schemaOnly`, `normalTurn`, `resumeOnly`, `resumeAtOnly`, `resumedFinal`. The probe sends no request. `freshFinal` opens a new session and starts its first turn as final. `schemaOnly` opens a separate new session whose first child receives the diagnose policy's `outputFormat`, with `sessionId` and without `resume`, then starts a non-final turn. Only `normalTurn` sends a user message, with a one-response backstop. `resumeOnly` opens a new adapter session with `resume` and without `resumeSessionAt` or `outputFormat`. `resumeAtOnly` also passes the normal turn's recorded resume point. Both start non-final turns. Session identity and the point come from the runtime, as in the [persistence checks](src/smoke-resume.ts), never from Claude Code's files. `resumedFinal` runs on the normal turn's original session.

If the normal turn starts more than one request, all three resume steps are skipped with `requestBudget`. If it cannot start or has no ending, they are skipped with `normalUnavailable`. If it returns no resume point, only `resumeAtOnly` is skipped with `normalUnavailable`. A failure in any step is recorded locally and the remaining steps continue.

The [smoke SDK wrapper](src/smoke-runtime.ts) refuses every offer except `normalTurn` without forwarding it to the child. A refused offer records `sendWithheld: true` and preserves the adapter's resulting failure. A diagnose-only flag injects the policy's schema into `schemaOnly`'s next open and is consumed by that open; selecting the child requires no option values. Without `--diagnose`, the SDK options and sends follow the full smoke unchanged. Persistence, fork and tool checks do not run in diagnose mode.

```sh
bun --no-env-file packages/runtime-claude/src/smoke.ts --live "$NEUVE_STATE" --diagnose
```

The JSON line contains `mode: "diagnose"`, probe counts, `turns.freshFinal`, `turns.schemaOnly`, `turns.normal`, `turns.resumeOnly`, `turns.resumeAtOnly`, `turns.resumedFinal`, total `requestsStarted` and `requestsCompleted`, `expectedRequests: 1`, `withinPlan` and `wallMs`. Request starts count distinct root message ids from `message_start` and `assistant` frames, plus API retries, before validation. Completions count `message.finished`. More than one start sets `withinPlan: false` and exits 1. A run within plan exits 0 even when a turn fails.

Each diagnosis, including the probe, includes an `opens` array. The [open observer](src/smoke-open.ts) labels each open `sdkOpen`, `initialization` or `effortUpdate` when that step fails, `timeout` when an open is interrupted before any step fails, or `ready` after initialization and any effort update succeed. Each record includes option booleans `resume`, `resumeSessionAt`, `sessionId`, `forkSession`, `continue` and `outputFormat`, without values. Its `child` record contains `stderrLines`, `exited` and any validated `errorClass`, integer `exitCode` or `signal`. The SDK's default process spawn remains in use.

Stderr classification spans chunk boundaries and retains no line or chunk. It reports the first error-shaped token only if it is tag-shaped. An optional fixed `marker` is the first match of `noConversation`, `noMessageAtUuid`, `dropGuardRefused`, `notAUuid`, `resumeLoadFailed`, `jsonSchemaNotJson`, `jsonSchemaNotObject`, `invalidSessionId`, `resumeNeedsValidId`, `sessionIdInUse`, `cannotBeCombined`, `requiresResume`, `noMessagesReturned`, `notValidJson`, `invalidSchema` or `schemaConversion`. `flag` retains the first allowlisted flag name matching `/--[a-z][a-z-]{1,40}/`; unknown names set `otherFlag: true` and are discarded. The fixed allowlist comes from SDK 0.3.316's `sdk.mjs:152`, `Iv.initialize()`, its `F6()` and `$6()` argument helpers, and the SDK's fixed extra arguments. Arbitrary `extraArgs` names remain untrusted. `errorPrefix` records whether any line starts with `Error:`. No flag value is retained. Neither stderr content nor the SDK's error message reaches logs or stdout. The [production SDK boundary test](tests/smoke-production-fixture.ts) verifies that only the three validated exit fields cross into `ClaudeSdkError`.

A start failure includes that turn's partial diagnosis, its `step`, `causeKind`, optional validated `errorTag` and contract `reason`. A probe or outer program failure prints `outcome: "failed"` with the current step and any collected diagnoses. Cause kinds are `fail`, `die`, `interrupt` and `timeout`. The five-minute deadline applies to both modes.

Observer failures report `observerError: true` and `observerErrorIn` as `begin`, `offered`, `receive`, `event`, `open` or `sdk`. Observers contain exceptions before they can enter the SDK or change adapter outcomes. A completed turn diagnosis includes its outcome status and any failure reason and disposition. `frameShapes` counts frames by type and subtype. `firedPath` names the first known adapter predicate that fails, `unclassified` for an unmatched protocol error, or `none`. `faultIsLastFrame` identifies whether that fault was the last received frame. The optional `faultingFrame` contains only tags, stamp presence and counts, stamp-match and null-parent booleans. Shape failures add schema paths and zod issue codes, without values. Array indices and provider record keys become `[]`. Header strings must match `/^[a-z][a-z0-9_]{0,39}$/`, otherwise they become `unrecognized`.

The [open-only tests](tests/smoke-open-only.test.ts) verify schema injection, resume options, withheld sends, failure isolation, request totals and private stderr classification through the production adapter. The [open-step tests](tests/smoke-open.test.ts) exercise each failure step, both resume paths, withheld sends and stderr privacy through the production adapter. The [output tests](tests/smoke-output.test.ts) verify one-line stdout, stderr logging and typed full-smoke failure. The [entrypoint tests](tests/smoke-diagnose.test.ts), [failure tests](tests/smoke-diagnose-failure.test.ts) and [regression tests](tests/smoke-diagnose-regression.test.ts) retain coverage of frame faults, retries, budget skips, observer errors and filtered headers.

The [tools-only diagnose arm](src/smoke-tools-diagnose.ts) runs only the probe and the unchanged tools check. Select it with `--live <absolute-state-directory> --diagnose-tools`. It forwards every tools message, including both held steers when their handlers run. It never withholds a send or adds a model request. Without this flag, the full smoke and `--diagnose` retain their existing behavior.

Its JSON line has `mode: "diagnose-tools"`, probe counts, the tools diagnosis and original tools checks, `expectedRequests: 1`, `requestsStarted`, `requestsCompleted`, `withinPlan`, `stoppedAtCap` and `wallMs`. Up to two observed starts are within plan. A third distinct root response or API retry triggers `interruptTurn` with reason `cutoff` before the adapter receives that frame, records `stoppedAtCap: true`, and exits 1. Within the cap, a protocol failure remains a diagnosis and exits 0. Probe or start failures retain the typed failure shape and exit 1.

`tools.frames` retains the first 200 frames in arrival order; `frameTotal` counts every frame, including the fault and frames the adapter suppresses. Each entry reports its type and subtype or stream event type, `validFrame`'s boolean result, null-parent and stamp-presence booleans, and whether stamps match offered messages. Rejected entries add schema paths and issue codes. Assistant and stream blocks retain only their types, with tool names mapped to `note`, `finish`, `StructuredOutput` or `other`. User entries report string content or block types and presence of `isReplay`, `isSynthetic`, `tool_use_result` and `priority`. No field value, message text, identifier, input, output, token count or filesystem path is retained.

The tools diagnosis also retains the existing first `firedPath` and child stderr and exit classifiers. It mirrors handler-start publication to identify later frames of a published response. An otherwise unclassified denied foreign tool or non-final `StructuredOutput` permission is identified as `canUseToolUnknown`. `canUseTool` records the fixed tool-name category and returned `allow` or `deny` behavior. `handlers.note` and `handlers.finish` each report `calls` and `returnedError`. The turn ending reports status and its contract reason when present. Observer exceptions remain contained. The [tools diagnose tests](tests/smoke-tools-diagnose.test.ts) exercise these records, both request-cap paths, the frame cap and output privacy through the production adapter with a replay SDK.

Those remain outside this live run. Persistence and CLI behavior remain unverified until the coordinator authorizes and runs the command.
