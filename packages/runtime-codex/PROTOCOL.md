# Codex app server: the facts the runtime relies on

**The design this table was first written for was replaced.** It was written to support a check at session open: read back from the running program its configuration, features, hooks, skills, MCP servers and apps, and refuse the session unless only Neuve's tools were left. The finding below stands as a fact. On 20 November 2026 the owner ruled that Codex keeps its own tools, as T3 Code has it ([the decisions record, Area 14](../../process/decisions.md#area-14-lane-assignment-and-agent-dispositions-redesigned-12-november-2026); the [Codex runtime proposal's tools section](../../process/proposals/codex-runtime.md#tools-codex-keeps-its-own-and-neuves-are-served-beside-them) follows it). So the check at open is dropped, and no revision of it is being chosen here.

The finding: at 0.171.0-alpha.13 every read-back reflects the command line, and each of the person's own settings can be switched off and is read back off. But OpenAI's source at this release registers tools for the model that none of the read-backs names:

- **File editing.** `apply_patch` is registered whenever the model's catalogue entry names a patch format ([`spec_plan.rs` line 1483](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/spec_plan.rs#L1483)). No feature gates it. In Codex's model cache on this machine, read once during this work and not kept, each of the three models read names the `freeform` format.
- **Tools the catalogue entry declares.** Its `experimental_supported_tools` adds more (lines 1386, 1414, 1442 and 1490).
- **Asking the user.** `request_user_input` is registered unless `tools.experimental_request_user_input.enabled` is set to false, and it is on when unset, whatever the catalogue says ([`spec_plan.rs` lines 1373–1380](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/spec_plan.rs#L1373); [`config/mod.rs` lines 2871–2877](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/config/mod.rs#L2871)).
- **Codex's MCP-resource tools** (list and read a server's resources) are added whenever any MCP server is configured, or in code-mode-only operation ([line 1329](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/spec_plan.rs#L1329)).

The plan tool is not among them: it is off by default, registered only when `tools.update_plan.enabled` is true ([`spec_plan.rs` line 1357](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/spec_plan.rs#L1357); [`config/mod.rs` lines 2879–2885](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/config/mod.rs#L2879)), which the launch configuration does not set: the kept recording reads back `tools: null`.

Traced: where tools are registered (`add_core_tool_sources`, called from `build_tool_router`, line 151) and the final filters (`finalize_tool_router`, line 401), which change what is visible only in code-mode-only operation or through a tool policy that a client cannot supply (below). No thread was started and no model turn was run.

## How the program was found and run

By the design's probe order applied by hand. The applications folders were read for the identifier `com.openai.codex`, and the app that carries it was used. Its `codex-package.json` has layout version 1, version `0.171.0-alpha.13`, target `aarch64-apple-darwin`, and entry point `bin/codex`, which is exactly the program in the package's own `bin` folder after links are followed (T3 Code's rule, `apps/server/src/provider/CodexInstallation.ts` line 255). A few lines of script printed that path, which each run took as `--program`. The handshake's version matched the manifest's.

Each run was `<program> app-server [-c key=value ...]` with the transport on standard input and output, through [`scripts/record.ts`](scripts/record.ts). Each had a new empty working folder under the temp directory, `CODEX_HOME` set to the person's own Codex home, and OpenAI's key and address variables removed (`REMOVED_ENVIRONMENT` there). Five runs. Which left a recording:

| Run | What it was | Recording |
| --- | --- | --- |
| 1 | The handshake | Kept: [`handshake.json`](tests/fixtures/handshake.json), trimmed |
| 2 | Read-only requests on the person's own configuration | Not kept. It held their whole configuration and was deleted |
| 3 | Under the launch configuration, exited on a quoting error of mine | None. The recorder of that time saved only after success; it now saves on failure too |
| 4 | Under the launch configuration | Not kept. It held the names of all the person's own settings and was deleted |
| 5 | Under the launch configuration, the person's skills switched off by name | Kept as [`read-only.json`](tests/fixtures/read-only.json), cut down by allow-list |

Run 2 ran with the person's hooks and MCP servers enabled in its configuration. It listed the hooks; no thread was started, and whether any hook or server process ran was not observed. Its `app/list` reached OpenAI's backend. Every working folder was still empty afterwards.

## The launch configuration

[`launchConfiguration`](scripts/steps.ts) in the recorder builds it, every value after `app-server` as `-c`:

- `features.<name>=false` for each feature this release enables by default that gives the model a tool, loads outside code, or is not on the replay judge's safe list ([`SAFE_ENABLED_FEATURES`](../evaluation/src/pr-replay/codex.ts)). `unified_exec` is on that list and is switched off here all the same, which Codex ignores (above).
- **Not yet one list with the replay judge's.** The design says the list is shared. This one (`DISABLED_FEATURES` in [`scripts/steps.ts`](scripts/steps.ts)) switches off twelve names the judge's Mac list does not: `tui_workspace`, `unified_exec`, `untrusted_as_tool_output`, `code_mode_host_grpc`, `code_mode_host_output_truncation`, `deferred_tool_world_state`, `incremental_tools_legacy`, `incremental_tools_legacy_gcp`, `unified_image_budget`, `guardian_include_additional_context`, `retain_client_tool_outputs` and `memories`. They are enabled by default in this release, or newer than that list. It leaves out two of the judge's (`plugin_discovery_prefetch`, `multi_agent_v2`), off by default here. Making them one list touches the judge's gate, so it is a follow-up.
- `web_search="disabled"`; `notify=[]`; `history.persistence="none"`; `approval_policy="never"`; `sandbox_mode="read-only"`; `shell_environment_policy.inherit="none"`; `project_doc_max_bytes=0`; `memories.use_memories=false`; `memories.generate_memories=false`; `agents.enabled=false`; `apps._default.enabled=false`; `skills.bundled.enabled=false`; `skills.include_instructions=false`; update checks, analytics and feedback off.
- By name, from the person's own configuration read first: `mcp_servers.<name>.enabled=false`, `plugins.<id>.enabled=false`, `apps.<id>.enabled=false`, and `skills.config=[{name=…,enabled=false}, …]`.

It leaves the model no tool that the read-back can name; Codex's own tools at the top remain. It is the recorder's, for the read-only runs; under the owner's ruling the runtime sets Codex's approval policy and sandbox for each turn instead.

## What else the source supports

Read at the tag, and recorded because the runtime slice may need them; none was tried.

- **Only the catalogue changes the catalogue's tools.** The configuration overrides applied to a model's entry touch none of `apply_patch_tool_type`, `experimental_supported_tools` or `tool_mode` ([`with_config_overrides`, `models-manager/src/model_info.rs` lines 19–59](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/models-manager/src/model_info.rs#L19)). For a model the catalogue does not know, Codex builds an entry with all three empty ([lines 97–145](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/models-manager/src/model_info.rs#L97)).
- **A client cannot supply a tool allow-list.** The policy (`ToolPolicy.allowed_tools`) reaches a thread only through its extension data ([`ext/extension-api/src/tool_policy.rs` lines 6–14](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/ext/extension-api/src/tool_policy.rs#L6)), which the app server's thread start fills with the selected capability roots alone ([`thread_processor.rs` lines 1630–1633](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server/src/request_processors/thread_processor.rs#L1630)). No field of the published `thread/start` or `turn/start` parameters carries it.
- **A read-only sandbox refuses a patch after reading its target.** With approval policy `never` and a read-only sandbox a patch is refused ([`core/src/safety.rs` lines 15–16 and 90–120](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/safety.rs#L15)), but verification reads the target first ([`apply_patch.rs` lines 478–516](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/handlers/apply_patch.rs#L478); [`apply-patch/src/invocation.rs` lines 210–233](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/apply-patch/src/invocation.rs#L210)), so the error returned to the model shows whether a file exists.

## Open for the runtime slice

The client leaves these to the slice that maps it onto the runtime contract:

- **Responses are cast, not decoded.** Each answer is given the generated type without being checked against it, so a field a later Codex renames or drops reaches the caller as missing, not as a failure.
- **The notification queue is unbounded.** The whole-range reviewer measured about 104 MB held at 200,000 unread notifications (not measured again here). The safer end state is a bound that ends the connection with a typed failure; it is to be decided where the reader of notifications exists, which is the runtime.
- **Replay matches method names only.** The replayer checks each outgoing line's method, or the id of an answer, and not its parameters.
- **Two feature lists.** The one in [`scripts/steps.ts`](scripts/steps.ts) must become one with the replay judge's before the runtime slice.

## What the generated types keep, and leave out

[`scripts/generate.ts`](scripts/generate.ts) takes OpenAI's published TypeScript at the tag (the stable surface: the experimental methods and fields are not in it), fetched at the commit the tag resolves to, which each file's header records; it refuses to regenerate from the same tag at another commit unless told to repin. It keeps 305 files: 19 client requests, 23 notifications and every server request, with what they import. It leaves out the other notification types (their names stay in `SERVER_NOTIFICATIONS`, so a known one is never mistaken for an unknown one), the other client requests, the JSON Schema form, the legacy `v1` folder and the precomputed export lists. Adding a method to its lists and running it again brings that method in.
