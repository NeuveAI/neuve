# Codex app server: the facts the runtime relies on

**The check at open is not shown sound, so the design stops here for revision.** The [Codex runtime proposal](../../process/proposals/codex-runtime.md#tools-neuves-are-the-only-ones) rests on one guard: before the first turn, read back from the running program its configuration, features, hooks, skills, MCP servers and apps, and refuse the session unless only Neuve's tools are left. On this machine at 0.171.0-alpha.13 every one of those read-backs reflects the command line, and each of the person's own settings can be switched off and is read back off. But OpenAI's source at this release registers tools for the model that none of them names:

- **File editing.** `apply_patch` is registered whenever the model's own catalog entry names a patch format ([`spec_plan.rs` line 1483](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/spec_plan.rs#L1483)). No feature gates it. In Codex's model cache on this machine, read once during this work and not kept, every model read (`gpt-6.2-sol`, the default, `gpt-6.2-astra`, `gpt-5.6-luna`) names `freeform`.
- **Tools the model declares.** The catalog entry's `experimental_supported_tools` adds more (lines 1386, 1414, 1442, 1490). The default model declares `clock` and `send_message_to_user_async`, which need nothing else, and `request_user_input_async`, which also needs a configuration value.
- **The plan tool** comes from a configuration value the reference does not list (line 1357).
- **Codex's MCP-resource tools** (list and read a server's resources) are added whenever any MCP server is configured (line 1329), and Neuve's own server would be one.

So under the launch configuration below Codex would still register its own file-editing tool for a turn, plus what the catalog entry declares, and nothing the client can read before the turn shows it. Traced: where tools are registered (`add_core_tool_sources`, called from `build_tool_router`, line 151) and the final filters (`finalize_tool_router`, line 401). Those filters change what is visible in code-mode-only operation, or through a tool policy that only Codex itself can supply, not a client (below).

**Whether code-mode-only operation is in force is unproved, and it could make things worse.** The tool mode comes from the model's catalog entry first and from features only when the entry names none (`requested_tool_mode`, [`tools/mod.rs` lines 69–78](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/mod.rs#L69)). The replay judge recorded a catalog entry that keeps code mode only ([`pr-replay/codex.ts`](../evaluation/src/pr-replay/codex.ts), lines 350–356), and this work read only three other fields of the entries here. If the default model's entry does the same, every tool sits behind the code-mode host, which the launch configuration switches off, and Neuve's own tools would be unreachable too. This rests on OpenAI's source and the catalog cache, not on a turn: seeing it live needs the turn the stop forbids. No thread was started and no model turn was run. Candidate revisions, each unproved, are at the end.

## How the program was found and run

By the design's probe order applied by hand. The applications in `/Applications` and `~/Applications` were read for the identifier `com.openai.codex`; one app carries it. Its `codex-package.json` has layout version 1, version `0.171.0-alpha.13`, target `aarch64-apple-darwin`, and entry point `bin/codex`, which is exactly the program in the package's own `bin` folder after links are followed (T3 Code's rule, `apps/server/src/provider/CodexInstallation.ts` line 255). A few lines of script printed that path, which each run took as `--program`. The handshake's version matched the manifest's.

Each run was `<program> app-server [-c key=value ...]` with the transport on standard input and output, through [`scripts/record.ts`](scripts/record.ts). Each had a new empty working folder under the temp directory, `CODEX_HOME` set to the person's own Codex home, and OpenAI's key and address variables removed (`REMOVED_ENVIRONMENT` there). Five runs. Which left a recording:

| Run | What it was | Recording |
| --- | --- | --- |
| 1 | The handshake | Kept: [`handshake.json`](tests/fixtures/handshake.json), trimmed |
| 2 | Read-only requests on the person's own configuration | Not kept. It held their whole configuration and was deleted |
| 3 | Under the launch configuration, exited on a quoting error of mine | None. The recorder of that time saved only after success; it now saves on failure too |
| 4 | Under the launch configuration | Not kept. It held the names of all the person's own settings and was deleted |
| 5 | Under the launch configuration, the person's skills switched off by name | Kept as [`read-only.json`](tests/fixtures/read-only.json), cut down by allow-list |

Run 2 ran with the person's hooks and MCP servers enabled in its configuration. It listed the hooks; no thread was started, and whether any hook or server process ran was not observed. Its `app/list` reached OpenAI's backend. Every working folder was still empty afterwards.

## The launch configuration

[`launchConfiguration`](scripts/steps.ts) in the recorder builds it, every value after `app-server` as `-c`:

- `features.<name>=false` for each feature this release enables by default that gives the model a tool, loads outside code, or is not on the replay judge's safe list ([`SAFE_ENABLED_FEATURES`](../evaluation/src/pr-replay/codex.ts)). `unified_exec` is on that list and is switched off here all the same, which Codex ignores (above).
- **Not yet one list with the replay judge's.** The design says the list is shared. This one (`DISABLED_FEATURES` in [`scripts/steps.ts`](scripts/steps.ts)) switches off twelve names the judge's Mac list does not: `tui_workspace`, `unified_exec`, `untrusted_as_tool_output`, `code_mode_host_grpc`, `code_mode_host_output_truncation`, `deferred_tool_world_state`, `incremental_tools_legacy`, `incremental_tools_legacy_gcp`, `unified_image_budget`, `guardian_include_additional_context`, `retain_client_tool_outputs` and `memories`. They are enabled by default in this release, or newer than that list. It leaves out two of the judge's (`plugin_discovery_prefetch`, `multi_agent_v2`), off by default here. Making them one list touches the judge's gate, so it is a follow-up.
- `web_search="disabled"`; `notify=[]`; `history.persistence="none"`; `approval_policy="never"`; `sandbox_mode="read-only"`; `shell_environment_policy.inherit="none"`; `project_doc_max_bytes=0`; `memories.use_memories=false`; `memories.generate_memories=false`; `agents.enabled=false`; `apps._default.enabled=false`; `skills.bundled.enabled=false`; `skills.include_instructions=false`; update checks, analytics and feedback off.
- By name, from the person's own configuration read first: `mcp_servers.<name>.enabled=false`, `plugins.<id>.enabled=false`, `apps.<id>.enabled=false`, and `skills.config=[{name=…,enabled=false}, …]`.

It leaves the model no tool that the read-back can name. It does not leave it only a client's tools, for the reason at the top.

## Candidate revisions, each unproved

Checked against OpenAI's source at the tag. What I could not confirm there is marked as the inner-loop reviewer's reading.

- **A model catalog Neuve supplies.** This is the only input found that changes the three fields at issue: `apply_patch_tool_type`, `experimental_supported_tools` and `tool_mode`.
  - **Configuration.** The configuration overrides applied to a model's entry touch none of them ([`with_config_overrides`, `models-manager/src/model_info.rs` lines 19–59](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/models-manager/src/model_info.rs#L19)).
  - **Fallback entry.** For a model the catalog does not know, Codex builds an entry with all three empty ([lines 97–145](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/models-manager/src/model_info.rs#L97)).
  - **Where the path shows.** A catalog path set with `model_catalog_json` would show in `config/read`, whose keys included `model_catalog_json` in run 2 (seen, not kept). An administrator's catalog would show in `configRequirements/read`, whose published type carries `modelCatalogJson` ([`ConfigRequirements.ts`](src/generated/v2/ConfigRequirements.ts)).
  - **What it leaves.** Two kinds of tool remain: the plan tool, and the MCP-resource tools. Per the reviewer's reading, the MCP-resource tools can only list and read the resources of configured servers, which would be Neuve's own server alone.
  - **Not traced to the end:** whether a supplied catalog fully replaces the one Codex downloads into its home. Seeing the effect would need one turn.
- **The tool allow-list cannot be reached by a client.**
  - **How it is supplied.** The policy (`ToolPolicy.allowed_tools`) is supplied only through a thread's extension data before the thread starts ([`ext/extension-api/src/tool_policy.rs` lines 6–14](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/ext/extension-api/src/tool_policy.rs#L6)).
  - **What the app server does.** Its thread start fills that data with the selected capability roots and nothing else ([`app-server/src/request_processors/thread_processor.rs` lines 1630–1633](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server/src/request_processors/thread_processor.rs#L1630)).
  - **The protocol.** No field of the published `thread/start` or `turn/start` parameters carries it.
  - **The reviewer's reading, not confirmed here:** that only Codex's internal reviewer inserts one.
- **A read-only sandbox is a backstop, not a guard.**
  - **Writes are refused.** With approval policy `never` and a read-only sandbox, a patch is refused with "writing is blocked by read-only sandbox" ([`core/src/safety.rs` lines 15–16 and 90–120](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/safety.rs#L15)).
  - **But the target is read first.** Verification runs before that check ([`core/src/tools/handlers/apply_patch.rs` lines 478–516](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/core/src/tools/handlers/apply_patch.rs#L478)). A deletion reads the whole file, and an update builds its diff from the file ([`apply-patch/src/invocation.rs` lines 210–233](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/apply-patch/src/invocation.rs#L210)).
  - **So the model can probe.** The error returned to the model shows whether a file exists. Per the reviewer's reading, it also shows whether guessed lines match.
- **Ruled out: the strict third-party mode.** It defers third-party tools in code-mode-only operation (`enforce_strict_3p_tools`, `spec_plan.rs` line 636). That would hide Neuve's tools, not Codex's own.
- **T3 Code's way.** Codex keeps its own tools under its sandbox and approvals. The proposal names this as the fallback and as the owner's choice.

## What the generated types keep, and leave out

[`scripts/generate.ts`](scripts/generate.ts) takes OpenAI's published TypeScript at the tag (the stable surface: the experimental methods and fields are not in it) and keeps 305 files: 19 client requests, 23 notifications and every server request, with what they import. It leaves out the other notification types (their names stay in `SERVER_NOTIFICATIONS`, so a known one is never mistaken for an unknown one), the other client requests, the JSON Schema form, the legacy `v1` folder and the precomputed export lists. Adding a method to its lists and running it again brings that method in.
