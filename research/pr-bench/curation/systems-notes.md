# Systems and DevTools review cases

The curated systems records (kept in the private archive) select eleven review flows and retain two rejected candidates. The capture verification (kept in the private archive) checks the saved bytes against per-case SHA-256 manifests. These are observations and proposed evaluation uses. They do not change Neuve's [established vocabulary](../../../vocabulary.md) or [quality and attribution priorities](../../../foundations/01-product-purpose.md).

## Mechanisms worth evaluating

A review finding is a supported claim about behavior. A contributor reply is a claimed correction or policy choice. A later patch is separate evidence about what actually changed. Connecting these three records is the task; collapsing them into a single final PR summary loses both the reason and the revision to which it applies.

| Proposed use | Concrete obligation exposed by these cases | Evaluation limit |
| --- | --- | --- |
| Review harness | Present only the revision and evidence available before a particular review. Ask whether the finding is supported and what remains unresolved. | Future comments and fixes leak the answer. Public approval is a historical event, not an independently adjudicated oracle. |
| Retrieval | Retrieve relevant callers, repository conventions and related active changes. The hooks removal caller and the conflicting Entire refactor require context beyond the immediate hunk. | A structural relationship supports investigation; it cannot prove the runtime outcome. Retrieval recall needs a manually verified evidence set. |
| Embedding | Test whether a concern expressed as a user symptom retrieves the implementing call path and prior discussion. Lock hangs and “Removed hooks” without removal are useful cross-vocabulary examples. | This sample demonstrates useful queries but contains no embedding comparison or measured model quality. |
| Enrichment | Preserve actor, source revision, reply target, tentative versus reproduced concern, accepted difference and linked correction separately. | Inferring “resolved” from an author saying “Done” would conflate a claim with verified correction. Thread resolution is only a current provider snapshot. |
| Reviewer skills | Check actual behavior rather than test counts; question missing authority; examine destination ownership; follow a shared helper through all callers. | Patterns are hypotheses for skills and evaluation tasks. A case does not establish language-specific product eligibility. |
| Batch overview and review desk | Surface the unresolved choice or new finding while retaining completed investigation. Pin the contextual marker to its supported hunk and source revision. | Historical public review lanes are unknown. Reconstructing them from approval or merge events would fabricate Neuve responsibility decisions. |
| Work disclosure | Show changed behavior, proof, limits and the decision still required. Preserve a compact latest briefing with drilldown to the detailed source. | More text is not automatically more useful. The mocked-test reviewer explicitly requested a shorter major-change description. |

These proposals serve Neuve's [reviewer's-tax principle](../../../foundations/05-reviewers-tax.md), which distinguishes unnecessary repetition, wrong attribution and missing attribution. The roots reviewer changing their mind is an attribution test. The hook-removal caller is a missing-context test. The reland patchset restructuring is a disclosure test. They need separate scoring.

## Selection and capture limits

The sample deliberately favors visible discussion. It cannot estimate how often these problems occur in popular repositories. The Entire cases include agent-generated work disclosures and bot reviews. GitHub `User` accounts are recorded as user accounts with unknown assistance; `Bot` accounts are separate. Gerrit service-account tags, messages, labels and copied-vote explanations are preserved in raw data.

Eight GitHub candidates were captured, including the [stale redirect-policy PR](https://github.com/ChromeDevTools/chrome-devtools-mcp/pull/2503), rejected as a positive exchange because the contributor did not substantively answer the inline findings. Five Gerrit candidates were captured, including the [HAR URL change](https://chromium-review.googlesource.com/c/devtools/devtools-frontend/+/8496184), rejected because eight patchsets contained only one LGTM discussion comment. Patchset count and review-message count are poor substitutes for actual back-and-forth.

GitHub captures include pull and repository metadata, code license, paginated reviews, inline comments, conversation comments, commits, changed files and timeline events. GraphQL adds current thread resolution and outdated flags. All 111 visible PR commits have file-patch captures. Nine additional reviewed commits missing from current MCP PR commit lists were recovered by SHA. These detached commits do not prove that all historical rebases and branch states are present. Complete historical source blobs and dependencies are not vendored, binary and large patches may be absent, and descriptions are editable snapshots.

Gerrit captures include change details, all visible revisions/commits/files, messages, labels with copy conditions, published comments and every visible patchset as base64 Git patches. The robot-comment endpoint returned HTTP 404. That is recorded as unavailable, not zero comments. Review happens at Chromium Gerrit; GitHub mirror activity is not substituted for it.

Code licenses are captured from each source. They do not establish rights to redistribute contributor discussion. Raw captures also contain public account metadata, so a publication copy needs rights and privacy decisions. No runtime reproductions or repository test suites were rerun. The records support review research now; a scored benchmark still needs pinned inputs, historical source reconstruction, environment constraints, independent finding adjudication and leakage controls.
