# Benchmark references for future PR Bench

Research snapshot, 2026-10-06. This survey supports the evaluation scope (NEU-14), which needs review-quality evidence rather than coding leaderboard substitution. It does not adopt a scoring policy. The [machine-readable catalogue](benchmarks.json) retains primary URLs, observed release revisions, reported sizes and ingestion checks. No model results were reproduced.

The closest reusable mechanisms are MCR-Bench's revision history, SWE-CARE's context experiments, SWRBench's clean-labeled controls, Martian/Kodus's inspectable scoring artifacts, and c-CRAB's executable correction checks. None alone measures how a contributor discloses work, how a reviewer reconstructs intent, and whether a discussion reaches a justified disposition.

An **oracle** is the evidence used to decide whether an answer earns credit. Human comments show what someone noticed; executable tests show behavior under their assertions. Both have incomplete coverage. **Leakage** occurs when a solver receives future answers or evaluation-only evidence. **Contamination** occurs when prior training has exposed an evaluation case or its answer. Temporal projection can prevent the former; public-source selection cannot guarantee prevention of the latter.

## What each benchmark actually exercises

Counts below are publisher-reported unless labeled as checked. Corpus languages describe coverage, never Neuve product eligibility. Precision is the proportion of reported findings that receive credit; recall is the proportion of reference findings recovered. Their meanings depend on each oracle.

| Benchmark and publication | Unit, size and solver input | Oracle and reusable mechanism | Limitation that changes interpretation |
| --- | --- | --- | --- |
| [CodeReviewer, ESEC/FSE 2022](https://arxiv.org/abs/2203.09095v2) | Local diff/code-review pairs across nine languages. Paper test sets approximately 31k quality-estimation, 10k comment-generation, 13k refinement examples. | Classification and reference-text/edit comparison; useful separation of review need, comments and contributor correction. | A similar comment can be incorrect; a correct comment can use different words. Local hunks omit repository obligations. The millions of pretraining examples are not the evaluation size. |
| [Nutanix CR-Bench, March 2026](https://arxiv.org/html/2603.11078v1) | 584 recovered defect-introducing PRs; 174 manually checked Verified tasks. Base repository and original PR reconstructed from later SWE-bench fixes. | Later issue descriptions paraphrased into references; judge distinguishes bug hits, valid suggestions and noise. | It retrospectively selects bugs, not naturally observed review interactions. References are incomplete. Verify blame linkage and exclude later fixes from solver access. |
| [Martian Code Review Bench, 2026 project](https://github.com/withmartian/code-review-benchmark) | Offline 50 PRs from five projects, 173 golden comments. Online fresh bot-reviewed PRs plus later developer commits. | Human-curated offline findings, category profiles, multiple judges and deduplication; online suggestion-to-fix matching. | Offline exposure and small samples; online fixes do not establish causality or correctness. Pin judge, profile and F-beta. Recent PRs reduce exposure risk without proving no leakage. |
| [Kodus CodeReviewBench, 2026 project](https://www.codereviewbench.com/) | 30 PRs and 95 golden findings, independently counted in released JSON. Frozen tool-response replay inside Kodus's agent. | Versioned submissions and scorecards; micro precision/recall/F1 judged by Haiku 4.5. | Existing scores compare models inside one vendor's agent. One agent run per model; repeated judging does not estimate generation variance. |
| [SWE-PRBench, March 2026](https://arxiv.org/html/2603.26130v1) | 350 PRs from 65 repositories; paper evaluates 100. Three frozen, bounded context configurations. | Mined human feedback and GPT-5.2 judge; reported validation agreement κ=0.75. Context experiments preserve exact input artifacts. | “Full context” is a bounded constructed prompt, not a full repository investigation. Added layers, budgets and summaries change together. Reported context degradation cannot establish that retrieval is generally unhelpful. |
| [ContextCRBench, November 2025](https://arxiv.org/html/2511.07017v1) | Quality estimation: 67,910 hunk entries. Localization and comment generation: 13,512 line entries each; paper samples 1,080. Linked issue/PR text and before/after function or class. | Quality classification, top-k line localization, ROUGE/edit similarity. Separate need, attribution and explanation tests. | Mining/filtering choices shape truth. Similarity does not validate semantics. Removing outdated anchors can erase the historical reasoning Neuve needs to retain. |
| [SWE-CARE / CodeFuse-CR-Bench, September 2025](https://arxiv.org/html/2509.14856v1) | Original 601 test cases from 70 Python projects; [current release](https://huggingface.co/datasets/inclusionAI/SWE-CARE) has 671 test / 7,086 dev cases. Issue, PR, exact commits and repository context. | Human reference reviews plus location/rule and model evaluation; none/BM25/oracle/all context conditions. | Oracle file selection uses future merged changes. Mark it as an upper bound. Its positive/negative reward heuristic combines changed lines and resolved threads; it is not a disposition oracle. |
| [SWRBench / SWR-Bench, September 2025, revised June 2026](https://arxiv.org/abs/2509.01494) | 1,000 PRs from 12 Python projects; 500 issue-bearing and 500 clean-labeled. Solver input is the PR state before its first manual review: title, description, prior commits and codebase checkpoint. Released timelines and extended commits retain construction evidence. | Structured introduced/discussed/resolved change points; functional and evolvability categories; PR-level and point-level metrics. | A clean label means no retained reference issue. It does not prove absence of defects. Released `pr_timeline` and `all_commits` can leak future answers when misused as solver inputs; the pinned README identifies `pr_commits` as the main input. |
| [MCR-Bench, August 2026; author-reported ISSTA acceptance](https://arxiv.org/abs/2608.27442) | Reported 2,269 multi-round tasks, five languages. Round diff, prior events and linked issues. | Defect identity/state cards across revisions; repeated annotation linking and model matching. | Direct artifact check found malformed JavaScript JSONL. Tasks count rounds rather than necessarily distinct PRs. State accuracy is conditional on detection; missed defects cannot disappear from an overall score. |
| [c-CRAB, March 2026, v3 April](https://arxiv.org/html/2603.23448v3) | SWE-CARE-derived subset. 410 filtered released cases; 184 final validated cases and 234 oracles. Per-case execution environments. | Convert human concerns into tests that fail before and pass after correction, then check whether a review-guided coding agent resolves them. | Outcome combines reviewer and fixer capability. Testability and solvability filter the corpus. v3 categorizes 192/234 tests as structural, so executable does not mean wholly runtime-behavior based. |
| [SWE-bench Verified, August 2024](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified) | 500 issue-resolution tasks; pre-fix repository and issue text. Agent writes a patch. | Fail-to-pass and pass-to-pass tests; reuse environment and log discipline. | This is patch generation. [OpenAI's audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) reports material flaws in 59.4% of a targeted 138 difficult tasks, not 59.4% of all 500. It also reports training exposure evidence for some cases. |
| [SWE-bench Multimodal, October 2024 / V2 September 2026](https://www.swebench.com/multimodal.html) and [Scale AI SWE-bench Pro, September 2025 / V2 September 2026](https://huggingface.co/datasets/ScaleAI/SWE-bench_Pro) | Visual-domain issue solving, V2 480 tasks. Pro long-horizon patch generation, V2 642 tasks with 51 HARD tasks; v1 731 retained. | Preserve image assets for UI work; pin environment and validate empty/reference patches. | Passing tests does not prove design quality or review judgment. The [July Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) estimates about 30% broken v1 cases. It does not validate September V2. |

The similarly named resources must stay distinct. Nutanix **CR-Bench** is neither Martian's **Code Review Bench** nor Kodus's **CodeReviewBench**. SWE-CARE is the released project associated with the paper **CodeFuse-CR-Bench**. The audio/text-conflict MCR-BENCH is unrelated to this code-review MCR-Bench. “CRBench” alone is ambiguous and should never be a dataset key.

## What Neuve can learn without importing a leaderboard

These are proposals grounded in the research, not established algorithms or new vocabulary. They serve Neuve's [product purpose](../../foundations/01-product-purpose.md), which requires verifiable work and concentrated human judgment, and its [reviewer's-tax measures](../../foundations/05-reviewers-tax.md), which distinguish repetition, wrong attribution and missing attribution.

| Neuve stage or surface | Dataset-derived experiment | What earns credit | What must stay separate |
| --- | --- | --- | --- |
| Harness | Replay a revision at the time it requested review; reveal contributor corrections and replies only after the reviewer acts. | Correct findings, precise source attribution, preserved unresolved obligations and scoped correction checks. | Overall PR merge, passing transport, and retained storage are not approval. |
| Retrieval | Compare diff-only, issue context, lexical retrieval, graph-backed ranked source evidence and an explicitly labeled oracle context. | Required source evidence retrieved at the correct revision and attached to the correct hunk; downstream review quality at measured input/output cost. | Missing source, missing returned metadata and unsupported inference are different failures. Rank is not sufficiency. |
| Embedding | Contrast comments describing the same issue with different wording, and similar wording about different versions. | Retrieval of the correct claim/source/revision; semantic deduplication that preserves provenance. | Embedding similarity cannot turn a reference comment into correctness evidence. |
| Ingestion and enrichment | Retain commit/review anchors, parent replies, evidence references, issue intent and later corrections with explicit timestamps. | Reliable temporal/source linkage and visible unavailable evidence. | A resolved thread or changed line is an observed event, not automatically a disposition or a proven fix. |
| Reviewer skills | Give paired cases where a concern is real, already fixed, unsupported, or a valid optional suggestion. | Evidence-backed escalation and correction, with justified abstention; detect reopened obligations. | Finding count rewards noise. Usefulness and certainty are separate dimensions. |
| Batch overview / review desk | Compare authored descriptions that disclose intent, alternatives, tests, screenshots and open questions. | Reviewers can locate the evidence and decide unresolved work without reconstructing its history. | Disclosure quality must not be inferred from comment count or persuasive prose. No broad UI redesign follows from this survey. |
| Records and lineage | Associate each concern with its original revision, later response, correction and verification evidence. | Reuse still-valid context and avoid asking again about a resolved unit without a new decision signal. | External GitHub discussion rounds are not automatically Neuve review cycles. A later relevant change requires fresh scoped review. |

A practical first experiment uses the same case at multiple cutoffs. At the first cutoff, a reviewer finds a real unresolved issue. At the next, a contributor has changed the relevant code but has not verified it. At a later cutoff, evidence establishes the correction. The harness asks different questions at those times. Treating every historical comment as a current defect gives a fluent reviewer an incorrect score and imposes unnecessary repetition on the human. MCR-Bench provides a starting pattern, while Neuve must retain its own disposition and cycle semantics.

The corpus should include negative examples that challenge the reference. A valid finding absent from human comments needs independent adjudication; an accepted suggestion with weak evidence must remain weak evidence. Preserve disagreement and uncertainty. Repeated runs and confidence intervals should accompany aggregate scores, with repository/PR-level grouping to prevent related rounds from leaking across splits. The [Kodus noise analysis](https://www.codereviewbench.com/blog/one-run-is-not-a-measurement) makes the difference between sampling variance, judge variance and unmeasured agent variance explicit.

## Remaining evidence gaps

The survey confirms primary publication metadata and release pointers. It does not establish current model superiority, full dataset correctness, or executable environment reproducibility. ContextCRBench bulk data access and several data licenses remain unresolved. Nutanix CR-Bench's reusable dataset/harness endpoint was not confirmed. MCR JavaScript needs upstream correction or an independently reviewed repair. c-CRAB's stage counts need reconciliation with exact files. External benchmark overlap must be deduplicated by repository, PR and commit rather than dataset name.

The most consequential missing evidence is whether a dataset's references cover what its solver is permitted to know. Before using a case for a scored task, inspect its complete provenance and produce the time-bounded solver projection. Keep gold findings, post-cutoff replies/fixes and later regressions in evaluator-only records. Public study cases remain useful for harness and retrieval development; a future scored holdout needs explicit exposure tracking and independent adjudication.
