# Sandboxing untrusted and generated code

Research, 2 November 2026. Nothing here is decided. It covers one part of the owner's multi-layered security model: where repository code, and code that agents generate, may run, what it may reach, and how that differs for each kind of session. Web sources were read on 2 November 2026. Vendor claims are marked as such. Anything not confirmed is marked **unverified**. Credential handling is covered in more depth by the sibling study, [secrets and exfiltration](04-secrets-and-exfiltration.md), which proposes the broker that holds credentials outside any sandbox. This study relies on that broker and does not repeat it.

## The short answer

- **No sandbox is in place yet where repository code actually runs.** Final review already runs no repository code, because its tools read Git objects only. Replay review on Modal is already well isolated. The gap is the coding session. Its `bash` tool starts a child process. That child runs as the owner, inherits the host's whole environment, and can read or write anything the owner can. That includes Neuve's own sign-in, Records, the run data on LaCie and other worktrees. The owner's named layer, that repository code never runs in Neuve's process, holds only in the narrow sense that it is a different process.
- **Layering, from cheapest to strongest.** (1) Neuve's process never loads repository code. (2) Each session kind gets only its own capabilities. (3) Every coding-session command runs under an OS sandbox. Writes are limited to its worktree, reads of credential and Records locations are denied, and the network is denied by default through a host proxy. (4) Credentials stay outside the sandbox, in the broker. (5) Hosted and multi-user work moves to one virtual machine per session. Locally, a VM per session is optional.
- **Smallest first step.** Wrap the coding host's execution environment with Anthropic's open-source sandbox runtime. On macOS that runtime uses Seatbelt. Stop the inheritance of the host's environment at the same time. pi already has the seam for this: one execution-environment function per conversation.

## What runs where today

These observations come from reading the rewrite at `de4a4832` on `codex/pi-transition`. The sibling study of Neuve today may describe them more fully.

| Session kind | What it executes | Current boundary |
| --- | --- | --- |
| Coding session (implementer in a lane's worktree) | pi's `CodingTools`: `read`, `write`, `edit` and `bash`. Each call goes through a [`NodeExecutionEnv` built per working directory](../../apps/neuve-host/src/worker.ts). pi's `bash` passes `inheritEnv: true`, so the child receives all of `process.env`. Cleanup on timeout or abort sends `SIGKILL` to the process group. | A separate process only. There is no filesystem limit, no network limit and no environment scrubbing. A child that calls `setsid` leaves the process group, so the cleanup misses it |
| Human terminal in the coding app | [A login shell with the host's environment](../../apps/neuve-host/src/terminals.ts) | None. It is the person's own shell, so this is acceptable for that person (see multi-user below) |
| Final-review session (Understand, Investigate, Assemble, Dispose) | Nothing from the repository. Its tools read Git blobs at the range's object IDs, and harness agents have no filesystem ([the harness proposal's isolation rules](../../process/proposals/m3-harness.md), section 3.6, ruled by decision 10.77) | A capability boundary: the tool list itself. Prompt injection can still steer what the review says |
| Neuve Graph | It parses source in its own Go process. Its C++ language-server step already runs `clangd` under [a Seatbelt profile with a scrubbed environment](../../apps/neuve-graph/internal/sem/lsp_enrichment.go) | That profile is a working local precedent for this study |
| Replay review on Modal | The Neuve binary, run against one pull request's clone | One Modal Sandbox per case. It mounts only that case's clone (`research/pr-bench/replay/modal/isolation.py`, kept in the private archive), reaches the network only on an allowlist of the model hosts and the lease host, borrows short-lived access through the lease, and never sees labels. Steps with nothing to call run with `block_network=True` (the orchestrator, `research/pr-bench/replay/modal/app.py`, kept in the private archive). This follows decisions 10.129 and 10.131 on moving replay to the cloud with its own sign-in |

The [release build](../../apps/neuve-cli/scripts/build.ts) already passes `--no-compile-autoload-dotenv` and `--no-compile-autoload-bunfig`. Without those flags, a compiled Bun binary started inside a repository loads that repository's `.env`, and its `bunfig.toml` `preload` would run repository code inside Neuve's process. Bun's documentation says the autoload is on by default ([Bun build options](https://bun.com/reference/bun/CompileBuildOptions), Bun 1.4.x). The evaluation package's [frozen-workspace build](../../packages/evaluation/src/neuve-build.ts) omits both flags. **Unverified:** whether that binary ever runs with its working directory inside an untrusted clone.

## Isolation tiers

| Tier | Boundary | What it does not cover | Cost | Fit for Neuve |
| --- | --- | --- | --- | --- |
| macOS Seatbelt (`sandbox-exec`, `sandbox_init`) | A kernel policy for each process tree: file, network, IPC, Mach | It shares the kernel and the user. Apple deprecates the command but it still works; community reports say it works on macOS 15 and no replacement exists ([apple/containerization issue 737](https://github.com/apple/containerization/issues/737)). **Unverified** on the current macOS | Near zero. Each command starts in milliseconds | **Local coding sessions, first step.** It is what Codex CLI, Claude Code and Neuve Graph's `clangd` step already use |
| Linux Landlock | Unprivileged self-restriction of files, TCP (ABI 4) and UDP (ABI 10), plus signal and abstract-socket scoping (ABI 6). Children inherit it ([kernel docs](https://docs.kernel.org/userspace-api/landlock.html)) | It cannot restrict `chmod`, `stat` and similar calls. The kernel stays shared | Near zero | A Linux local mode, as a second layer inside containers |
| seccomp and bubblewrap | Syscall filtering, and namespaces built without root, which give a private mount and network view | The kernel is shared. Unprivileged user namespaces are restricted on Ubuntu 24.04 and later | Low | The Linux counterpart of Seatbelt. Codex CLI and Claude Code use it ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)) |
| Containers, rootless or not | Namespaces and cgroups | The host kernel is shared, so a kernel bug escapes it. Docker Desktop on a Mac runs one Linux VM that all containers share | Low | Packaging, not a security boundary on its own |
| gVisor | A user-space kernel, the Sentry, that implements system calls. The host sees a short, fixed list of calls ([gVisor security model](https://gvisor.dev/docs/architecture_guide/security/)) | Hardware side channels and resource exhaustion. Its own documentation says a sandbox is no substitute for a secure architecture | System calls and I/O are slower | Modal's default runtime. Good for many tenants |
| Firecracker and other microVMs | KVM hardware virtualisation, five emulated devices and a jailer ([Firecracker](https://firecracker-microvm.github.io/)) | Side channels, and whatever the guest is allowed to reach | Vendor figures: under 125 ms to boot, under 5 MiB of overhead | The tier for hosted coding sessions with many users. E2B, Vercel Sandbox and Docker Sandboxes are built on microVMs (vendor claims) |
| Apple `container` | One lightweight Linux VM per container, macOS 26 ([The Register, June 2025](https://www.theregister.com/2025/06/10/apple_tries_to_contain_itself/)) | It runs Linux, not macOS, so macOS-only toolchains cannot run in it | Under a second to start (vendor claim) | A later local mode for an "untrusted repository" setting on Apple silicon |
| V8 isolates (Cloudflare Workers) | Memory isolation inside a shared process. Capabilities exist only as bindings ("no API means no access"). Cordons, a process sandbox and Spectre mitigations add defence in depth ([Workers security model](https://developers.cloudflare.com/workers/reference/security-model/), updated 18 October 2026) | Native binaries cannot run, so `git`, `bun test` and compilers cannot either. Local `workerd` lacks several of these protections | Lowest | **Neuve's own hosted logic.** It cannot run repository code |
| Cloudflare Containers and the Sandbox SDK | Each instance is a microVM with its own kernel, driven from a Durable Object ([Sandbox SDK](https://developers.cloudflare.com/sandbox/), updated 30 September 2026). Outbound Workers add allow and deny host lists, credential injection from outside the sandbox and TLS interception, and policy can change for each instance at run time ([changelog, 13 April 2026](https://developers.cloudflare.com/changelog/post/2026-04-13-sandbox-outbound-workers-tls-auth/), `@cloudflare/sandbox` 0.8.9) | The Durable Object scheduling policy is in beta. Limits are on separate pages | Workers Paid plan | **The hosted coding session's tier**, matching the hosted direction in [decision 10.92](../../process/decisions.md), which names Cloudflare Workers, queues and Durable Objects as a hosted platform |
| Modal Sandboxes | gVisor or a KVM VM. The network can be blocked, limited to CIDR ranges, or limited to TLS domains (beta, matched on SNI). By default a sandbox cannot reach the rest of the workspace ([Modal sandbox networking](https://modal.com/docs/guide/sandbox-networking)) | DNS stays open unless the whole network is blocked. Domain fronting can bypass the domain list | Billed per second | **Replay review, as it stands.** Keep it |
| E2B and Daytona | VMs created on demand (E2B: [docs](https://docs.e2b.dev/)). Daytona offers CIDR allowlists or block-all, and its lower tiers are restricted ([Daytona network limits](https://www.daytona.io/docs/en/network-limits)) | Isolation details were not confirmed from primary pages | Vendor pricing | Alternatives only. Neuve already has Modal and leans to Cloudflare |
| Devcontainers | A way to describe an environment, not a boundary. `initializeCommand` **runs on the host** ([devcontainer reference](https://containers.dev/implementors/json_reference/)) | Repository-defined lifecycle commands, mounts and `privileged` | — | Never honour a repository's `devcontainer.json` without review |

## How current agent tools isolate execution

| Tool | What runs in the agent's own process | What runs isolated, and how |
| --- | --- | --- |
| OpenAI Codex CLI | The model loop and the file tools | Commands run under the `read-only`, `workspace-write` or `danger-full-access` modes, using Seatbelt on macOS and bubblewrap on Linux ([Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing.md)). In `workspace-write`, the network is off unless `network_access = true` (from the official page as indexed by search; the page read on the day stated no default, so **partly unverified**). Neuve's labeller already calls `codex exec --sandbox read-only` ([replay Codex route](../../packages/evaluation/src/pr-replay/codex.ts)) |
| Claude Code | `Read`, `Edit` and `Write`, hooks, local MCP servers and the language server all run **outside** the sandbox and are governed only by permission rules | Bash runs under Seatbelt or bubblewrap. Writes are limited to the working directory. Reads are broad by default. The network goes through a host proxy whose allowlist starts empty. `.git/hooks`, `.git/config`, `.mcp.json` and settings stay write-protected even inside writable folders. Credentials can be denied or masked, with the proxy injecting the real value ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). Anthropic reports 84% fewer permission prompts. On the web, a git proxy holds the real token outside the sandbox ([Anthropic engineering, 20 October 2025](https://www.anthropic.com/engineering/claude-code-sandboxing)). The runtime is Apache-2.0, in beta, and usable as a library ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)) |
| OpenHands | The controller | A Docker sandbox by default. A process mode is labelled "unsafe" ([OpenHands sandboxes](https://docs.openhands.dev/usage/runtimes/overview)) |
| SWE-agent | The agent | SWE-ReX runs commands in Docker, Modal or a remote machine through a small server inside the sandbox ([SWE-ReX](https://github.com/SWE-agent/SWE-ReX)). Its hardening is not documented |
| Devin | The "brain", in the vendor's tenant | A new VM for each session, which can sit in the customer's VPC. Secrets are loaded as environment variables when the session starts ([Devin VPC docs](https://docs.devin.ai/enterprise/vpc/overview)) |
| GitHub Copilot cloud agent | GitHub's service | An Actions runner or cloud sandbox with a firewall. The firewall covers only processes started by the agent's Bash tool, not MCP servers or setup steps ([firewall docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)). Pushes go only to `copilot/` branches, workflows wait for human approval, and events from untrusted users are ignored ([risks and mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)) |

The common pattern: the agent loop and its credentials stay outside, and only commands go inside a sandbox. Two gaps recur. File tools outside the sandbox are governed by rules, not by the OS. Side processes such as MCP servers and setup steps escape the firewall.

## Egress, filesystem, resources and cleanup

- **Default-deny egress through a host proxy.** This is the strongest common practice, used by Claude Code, Codex, Docker Sandboxes and Cloudflare outbound Workers. A hostname allowlist sees only names unless TLS is terminated. Known bypasses: DNS left open (Modal says so of its domain list), domain fronting, and hostnames that resolve to loopback or metadata addresses. Anthropic's runtime refuses names that resolve to loopback, link-local or metadata addresses.
- **Filesystem.** The worktree is writable. Git metadata, settings and hook folders are write-protected. Credentials, Records and run-data locations are denied for reading. Claude Code's default of broad reads is the weak spot, and Neuve should not copy it: its own sign-in in `~/.config/neuve/` and its keys in `.env.local` must be unreadable to sandboxed commands. This follows [decision 2.16, keeping codebase facts apart from agent work](../../process/decisions.md).
- **Resources.** [Decision 6.10](../../process/decisions.md) says Neuve's work is never unbounded, and the machine's **capacity** in threads already bounds heavy jobs. Commands inside a sandbox need their own bounds: a wall-clock timeout (pi has one per call), `nice`, open-file and process limits, and container CPU and memory limits in hosted mode (replay already sets `cpu=4` and `memory=8192`). **Unverified:** how well memory limits are enforced for each process on macOS.
- **Process-tree cleanup.** Killing a process group misses children that call `setsid` or daemonise. Linux cgroup v2 `cgroup.kill` and VM teardown are complete. macOS has neither. Locally, the practical answer is to end the sandboxed tree when its session ends and accept the leftover risk. In hosted mode, the instance is destroyed.

## Multi-user and multi-tenant concerns

- **Locally it is already multi-user.** Under [decision 12.14](../../process/decisions.md), Ace's tailnet default joins the host to the team's tailnet and directory. If a teammate's chat can start a coding session on the owner's Mac, that teammate's prompts run `bash` as the owner. **Unverified:** whether remote chats can start `bash` on another person's host. If they can, a sandbox for each session is required before any VM work.
- **Isolate each session, not each user.** One sandbox or VM per coding session, never reused across users. Replay already does this per case.
- **Credentials separate per tenant.** No tenant's token is ever inside a sandbox. The broker injects a scoped credential for each request (the Claude Code web git proxy and Cloudflare outbound Workers do this). Decisions 6.6 and 10.5 (no Neuve auth, credentials read at run time and passed only to the call that needs them) already point this way.
- **Noisy neighbours.** CPU and memory limits for each instance, plus admission through the job queue, under decisions 6.10 and 10.91 on bounded concurrency.
- **Shared caches are an attack path.** GitHub Actions cache poisoning let untrusted pull-request code write caches that trusted release jobs later read ([Adnan Khan, May 2024](https://adnanthekhan.com/2024/05/06/the-monsters-in-your-build-cache-github-actions-cache-poisoning/)). Package, build or Graph caches shared between sessions must be read-only to sandboxes, or kept separate for each tenant and trust level. On Cloudflare, Workers' own cordons group tenants by trust level for the same reason.

## Prompt injection that leads to code execution

Repository content is untrusted input for every Neuve agent. Documented cases:

- **A code-review product ran a repository's linter configuration.** CodeRabbit ran RuboCop with a repository's `.rubocop.yml`, which loaded attacker Ruby code. The server's environment held the GitHub App private key and provider keys, which gave write access to about a million repositories ([Kudelski Security, 19 August 2025](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories)). This is the closest precedent for Neuve. Never run repository-configured tools, and never where credentials are reachable.
- **Agents rewrote their own permissions.** Injected text made Copilot set `chat.tools.autoApprove` in `.vscode/settings.json` and then run commands ([Embrace The Red, CVE-2025-53773](https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection)). This is why settings and hook files are write-protected inside sandboxes.
- **Agents in CI leaked secrets.** In April 2026, pull-request titles and comments steered Claude Code Security Review, the Gemini CLI Action and the Copilot agent into printing secrets from their environment. All three vendors fixed it ([CSA research note, 17 April 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-comment-control-github-prompt-injection-20/); the primary write-up was not reached).
- **Malware drove installed agent CLIs.** The s1ngularity Nx compromise ran local AI CLIs with `--dangerously-skip-permissions` to hunt for secrets ([StepSecurity, August 2025](https://stepsecurity.io/blog/supply-chain-security-alert-popular-nx-build-system-package-compromised-with-data-stealing-malware)). Malicious dependencies inside the worktree run during `bun install` and tests, so a coding session's sandbox must contain them too.

The design rule that limits the damage: a session should not combine untrusted input, private data and a way to send data out ([Willison, 16 June 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/); Meta's "Agents Rule of Two", 31 October 2025, as summarised in [Willison's note](https://simonw.substack.com/p/new-prompt-injection-papers-agents)). Every Neuve session reads untrusted input. So the sandbox has to remove the private data (credentials, Records, labels, other users' work) and the way out (default-deny egress). Filtering prompts is not a reliable defence.

## Recommended layering for Neuve

| Layer | What it guarantees | Local | Hosted |
| --- | --- | --- | --- |
| 1. Neuve never loads repository code | Repository files are read as data only. Neuve never imports or requires a repository file, honours no repository `bunfig.toml`, `.env`, `.mcp.json` (already refused by [the integration schema](../../architecture/decisions/0014-ace-style-pi-harness.md)), devcontainer or linter configuration. Neuve's own `git` runs with hooks, fsmonitor and other config-driven programs turned off | Keep the release build's no-autoload flags and add them to the evaluation build. Pass `-c core.hooksPath=/dev/null -c core.fsmonitor=false` to Neuve's own `git` | The same |
| 2. Capability by session kind | Coding sessions write only in their worktree. Final-review sessions keep their restricted tools and frozen submitted source. Replay review sees no labels, later revisions, research notes or credentials. Neither inherits the other's capabilities, as [the pi harness record](../../architecture/decisions/0014-ace-style-pi-harness.md) requires | Separate execution-environment factories for coding and review. The review one has no `bash` | The same, enforced by which bindings each Durable Object or Worker receives |
| 3. OS sandbox per command | Coding-session commands can write only the worktree and temporary folders, cannot read credential, Records or run-data paths, cannot rewrite Git or agent settings, and have no direct network | The Seatbelt-backed sandbox runtime wraps `NodeExecutionEnv.exec`, with `inheritEnv: false` and an allowlisted environment | Landlock or seccomp as a second layer inside the VM |
| 4. Credentials outside | No token in any sandbox. Requests to allowed hosts get a scoped credential injected by the broker ([sibling study](04-secrets-and-exfiltration.md)) | The proxy in the sandbox runtime, with masking. TLS termination is experimental | Outbound Workers with credential injection. The Modal lease stays as it is |
| 5. Default-deny egress | Only the model hosts and approved registries are reachable, through the proxy. Names resolving to loopback or metadata addresses are refused | The sandbox runtime's proxy | Outbound Worker allowlists. Modal's domain allowlist for replay, noting that DNS stays open |
| 6. A VM per session | A kernel bug or a same-user escape does not reach the host or other tenants | Optional: Apple `container` or Docker Sandboxes for repositories marked untrusted | **Required** for coding sessions: Cloudflare Containers through the Sandbox SDK. Review logic can stay in Workers, because its tools need no native code. Graph and anything native stays in a container |
| 7. Bounds and teardown | No command or session runs unbounded or outlives its session | Capacity grants, `nice`, timeouts, killing the tree at session end | Instance CPU and memory limits, then the instance is destroyed |

By session kind:

| Session kind | Local tier | Hosted tier |
| --- | --- | --- |
| Coding session, writing in its worktree | Seatbelt sandbox, worktree writable, no environment inheritance, egress through the proxy | A Cloudflare Container per session, outbound Worker allowlist, credentials injected |
| Final-review session, restricted tools and frozen source | No code execution. Neuve's process reads Git objects. Language-server steps stay under Seatbelt, as Graph's `clangd` step does today | A Worker or Durable Object with Records and Git-object bindings only. Native Graph work runs in a container with the network blocked |
| Replay review | — | A Modal Sandbox per case, as built. Keep the per-case mount, the allowlist and the lease, and block the network on steps with nothing to call |

## Smallest first step

1. In the coding host, replace the plain `NodeExecutionEnv` with one that turns off environment inheritance, passes an allowlisted environment, and wraps each command with `@anthropic-ai/sandbox-runtime`'s `wrapWithSandbox`. The policy: write to the worktree and a temporary folder for the session. Deny reads of `~/.config/neuve`, `~/.ssh`, `.env.local`, the Records store and the LaCie research and run folders. Deny writes to the Git common directory's `config` and `hooks`. Allow the network only through the proxy, to the model and package hosts.
2. Add `failIfUnavailable`-style behaviour: if the sandbox cannot start, refuse rather than run unsandboxed.
3. Add the no-autoload flags to the evaluation build. Harden Neuve's own `git` calls.

This needs no new product terms and no change to the review path. It closes the largest gap: generated code and dependency scripts reading Neuve's sign-in or the run data.

## What each step does not cover

- **Seatbelt** shares the kernel and the user. It does not stop kernel or same-user escapes. It depends on a deprecated Apple command. It does not stop exfiltration through allowed hosts, or through tunnels the proxy cannot see unless TLS is terminated.
- **Proxy allowlists** do not stop data from leaving through an allowed host. Code can still push secrets to an allowed registry or to the model provider itself.
- **Credential injection** does not stop a session from misusing the scoped credential it is given. Scope must be narrow: one repository, one branch, as GitHub's `copilot/` branches are.
- **VMs** do not stop side channels, or misuse of whatever the VM is allowed to reach.
- **Process-group cleanup** misses daemonised children on macOS.
- **No sandbox stops prompt injection from changing what a review says.** Final review's protection is that it holds no credentials and no way to execute code, and that a completed execution never grants approval. A human gate and recorded dispositions remain the control.

## Possibly wider than needed

- A VM per session locally for every repository. Seatbelt plus the credential broker covers the main local threat at almost no cost. Keep VMs for hosted work and for repositories marked untrusted.
- gVisor or Firecracker run by Neuve itself. Modal and Cloudflare already provide those tiers.
- Sandboxing final-review sessions. They execute nothing. Hardening Graph's native steps covers what is left.
- TLS interception of all egress locally. It is experimental and breaks certificate pinning. Use it only where credential masking needs it.

## Open points

- Whether teammates on the tailnet can start `bash` on another person's host. This decides how urgent the first step is.
- How macOS limits memory for each process, and whether a session-wide kill can be made reliable without a VM.
- The default network setting of Codex `workspace-write`, which the page read on the day did not state.
- Whether the evaluation package's frozen-workspace binary ever runs from inside an untrusted clone.
- Which package registries coding sessions may reach, and whether `bun install` runs inside the sandbox or in a separate step with network access before the agent starts, as Codex cloud does (**unverified** for the current Codex).
