# A shared Graph service and its clients

Research date: 23 October 2026. Status: research and proposals, with the owner's answers of the same day recorded in section 7; nothing here is built except what section 1 names. It answers the owner's ask after the [local search research](06-local-search-under-a-machine-budget.md) and decision 10.108: how other local code graphs and analysis services handle one shared instance per machine, many client processes, interactive against background work, precomputation, shared caches and bounded disk, and how Neuve's harness should use the one shared Graph instance the owner has decided on without Graph being the bottleneck. The [architecture record for Graph search](../architecture/decisions/0013-graph-search-service.md) turns it into the direction future work follows. The source notes hold what each outside source says, with its figures, in five parts: shared daemons, scheduling and priority, precomputation, caches and disk, and agents' retrieval. All five are kept in the private archive.

## In short

Tools that share one analysis service across many client processes all do the same few things. They find the daemon at an address derived from the user and the binary's build, and they settle a start-up race with a lock taken before the daemon binds. Inside, they run work as **small keyed tasks in a priority queue**. Concurrent callers share one execution per key, and an interactive caller raises the priority of queued work it now waits on. Nobody lifts a process that is already running. Ahead of time they compute cheap content-keyed facts for every commit, but the expensive whole-tree work only for the few bases that queries will actually use, and they collapse bursts of commits to the newest one. Disk stays bounded by a size cap plus an age rule, and nothing is evicted while a live client holds it. For Neuve this means that **the shared Graph instance has to be a scheduler, not just a long-lived process**. Saving process start-up is worth tens of milliseconds next to a median search of 11.3 s. The real gains are deduplication, batching per base tree, promotion inside the queue and one bounded cache. On the harness side, the three callers (a review's lead searches, agents' `graph_search` calls and commit preparation) should become thin clients. Each sends keyed requests with a class and a deadline to the one instance. Each reads stored answers first and never lets a review wait on Graph without a bound. Today's per-process slot, separate clones and parent-only snapshots go away. The ranked list in the last section separates what the harness must do from what the Graph instance must provide.

## 1. The starting point: three callers, three copies, one slot each

Today the harness runs Graph as a new process per search. A process-wide semaphore of one admits one search or one preparation at a time, at nice 10 with two threads ([graph-search.ts](../packages/harness/src/graph-search.ts)). Commit preparation runs in its own child process. It keeps its Graph clone and snapshots in a separate `graph-commit` folder, because "preparing moves the clone's HEAD, so the worker's review and this child sharing a clone would break each other's preparations". It runs its hunks' lead searches **one after another**, stops starting new ones after three minutes or three failures in a row, and leaves the rest to the review ([commit-prepare.ts](../packages/harness/src/commit-prepare.ts)). Each `graph_search` call an agent makes is bounded at 45 s, and that bound includes the wait for the slot and for base preparation ([search-config.ts](../packages/harness/src/search-config.ts)). The machine-budget design already concedes its own limit here. When a review waits on a key that background work holds, only the holder's *pending* grant requests can move to the interactive class, because "a running child keeps its class" and a background class cannot be lifted from outside ([machine-budget.md](../process/proposals/machine-budget.md)). The owner has since ruled that Graph's searches are made fast first and that "a shared Graph service for the machine is planned now" (decision 10.108, [decisions.md](../process/decisions.md)). The question is what that service and its clients must do so the queue, not the process count, sets Graph's latency.

The size of the gap matters. In the end-to-end check, BM25 answered at a median of 12 ms, embeddings at 107 ms and Graph at **11.3 s** ([research 06](06-local-search-under-a-machine-budget.md)). Cognition's context-retrieval subagent targets a **5-second window for a whole run** of up to four turns of eight parallel calls. It estimates that the chance of breaking a user's flow rises about 10% for each second of waiting, and it finds retrieval taking over 60% of a first turn ([Cognition](https://cognition.com/blog/swe-grep)). Cursor built a local regex index because agents waited more than 15 s for `rg` in monorepos ([Cursor](https://cursor.com/blog/fast-regex-search)). A Graph call is two orders of magnitude over these per-call targets. Faster searches alone will not close that gap. Graph also has to come off the agent's serial path.

## 2. Every shared daemon is found by identity and elected by a lock

The daemons studied find their server at a **deterministic address derived from identity**. gopls hashes the binary's Go build id into a per-user socket name under `$XDG_RUNTIME_DIR`, so a rebuilt binary gets its own daemon ([autostart_posix.go](https://github.com/golang/tools/blob/master/gopls/internal/lsprpc/autostart_posix.go)). It switched to that directory after editors that gave each process its own `$TMPDIR` produced one daemon per editor ([golang/go#41266](https://github.com/golang/go/issues/41266)). Watchman moved off `$TMPDIR` for the same reason ([Watchman CLI options](https://facebook.github.io/watchman/docs/cli-options)). Nx tries an ordered list of socket directories so that agent sandboxes, which allowlist fixed prefixes, can still reach it ([Nx Daemon](https://nx.dev/docs/concepts/nx-daemon)). The robust way to settle a start-up race is **an exclusive lock taken before the server binds**. Watchman locks its pid file "before we daemonize" ([main.cpp](https://github.com/facebook/watchman/blob/main/watchman/main.cpp)), Bazel takes an `fcntl` lock on the output base ([blaze.cc](https://github.com/bazelbuild/bazel/blob/master/src/main/cpp/blaze.cc)), and Buck2 holds a lifecycle lock "such that only one daemon is ever started per daemon directory" ([connect.rs](https://github.com/facebook/buck2/blob/main/app/buck2_client_ctx/src/daemon/client/connect.rs)). Mercurial's chg binds a private socket and renames it into place, which is lock-free but lets two servers briefly coexist ([chgserver.py](https://www.mercurial-scm.org/repo/hg/raw-file/tip/mercurial/chgserver.py)). gopls does neither, and its source carries a TODO admitting a race between simultaneous starters ([dialer.go](https://github.com/golang/tools/blob/master/gopls/internal/lsprpc/dialer.go)). The budget host's `BEGIN IMMEDIATE` claim on `budget.sqlite` already belongs to the robust family, so the Graph instance can reuse that election rather than invent one.

Version compatibility is always an **exact match**, never a semver range. Bazel kills a server whose version or start-up options differ ([Bazel client/server](https://bazel.build/run/client-server)). Buck2 records a named reason for every constraint mismatch that forced a restart ([connect.rs](https://github.com/facebook/buck2/blob/main/app/buck2_client_ctx/src/daemon/client/connect.rs)). Gradle only lets a client see daemons of its own version ([Gradle daemon](https://docs.gradle.org/current/userguide/gradle_daemon.html)). Since Neuve builds Graph per checkout and also installs a CLI copy, "one per machine" means in practice one per (user, Graph build). A build id in the address plus a check after connecting keeps a worktree's experimental build from serving the installed CLI's reviews.

Idle exit ranges from gopls's one minute to Bazel's, Gradle's and Nx's three hours. Watchman never exits, but it reaps idle watches after five days ([gopls daemon.md](https://github.com/golang/tools/blob/master/gopls/doc/daemon.md), [Nx Daemon](https://nx.dev/docs/concepts/nx-daemon), [Watchman config](https://facebook.github.io/watchman/docs/config)). Memory is guarded by exiting under low system memory (Bazel's `--shutdown_on_low_sys_mem`), or by Gradle's rule to "finish the currently running build" and restart before the next when a leak is detected ([Gradle daemon](https://docs.gradle.org/current/userguide/gradle_daemon.html)). When a daemon crashes, its in-flight requests die with it in every tool read. Recovery is always "the next client finds no server and starts one". That is tolerable only because these tools keep their durable state on disk. Graph's snapshots are on disk and its searches are idempotent against a fixed tree, so a client can safely retry once on a fresh instance.

The cautionary evidence counts as much as the patterns. gopls warns that a client of its daemon "shares the cache, the memory, and the fate of all other clients", and that the memory saved equals only the overlap between sessions' caches ([gopls daemon.md](https://github.com/golang/tools/blob/master/gopls/doc/daemon.md)). Two projects have moved work *out of* their daemons. Turborepo no longer uses its daemon for `turbo run` ([Turborepo run reference](https://turborepo.com/docs/reference/run)). sccache now recommends a client-side mode, in which compilation runs in the CLI and the daemon is only a shared gateway to storage and statistics. That mode "is expected to become the only supported configuration" ([sccache Configuration.md](https://github.com/mozilla/sccache/blob/main/docs/Configuration.md)). sccache also fails the build when the server is unreachable, unless `SCCACHE_IGNORE_SERVER_IO_ERROR=1` is set to fall back to the local compiler ([sccache README](https://github.com/mozilla/sccache/blob/main/README.md)). Published warm-versus-cold gains for start-up-bound daemons are small: chg saved "about 50-100msec on each command" ([Nishihara, 2011](https://www.mercurial-scm.org/pipermail/mercurial/2011-December/041265.html)). So the shared Graph instance does not pay for itself by staying warm. It pays for itself by being the single place where Graph work is deduplicated, batched, prioritised and stored. Without those it would be only a process with shared fate.

Concurrency models vary, and the choice decides whether the instance becomes the new bottleneck. **Bazel serves one invocation at a time**, and scripts wait behind interactive builds unless they use a second server ([Bazel scripts](https://bazel.build/run/scripts)). Gradle starts another daemon when the existing one is busy. **Buck2 runs concurrent commands in parallel when their state is the same** and blocks or preempts them when it differs ([Buck2 common issues](https://buck2.build/docs/users/faq/common_issues/), [common options](https://buck2.build/docs/users/commands/common-options/)). gopls hosts many sessions over one shared cache. Graph's searches read immutable per-commit snapshots, so Buck2's rule fits. Reads of a prepared snapshot can run in parallel, and preparing a new snapshot is a different state that must not block them. Bazel's one-at-a-time lock would reproduce today's single slot at machine scale.

| Concern | Strongest precedent | What the Graph instance inherits |
| --- | --- | --- |
| Address | gopls build id in socket name; Nx sandbox-safe directories | Per-user path outside `$TMPDIR`, keyed by Graph build id, allowed in agent sandboxes |
| Election | Watchman, Bazel, Buck2 lock before bind | Reuse the budget host's `BEGIN IMMEDIATE` claim pattern |
| Version | Bazel, Buck2 exact-match check after connect | Refuse a mismatched build; the client falls back |
| Concurrency | Buck2 same-state parallelism | Parallel reads per snapshot; preparation is its own lane |
| Failure | sccache fallback flag; Watchman `--no-spawn` client mode | A per-search process as the disclosed fallback (10.94's exception) |
| Lifetime | Gradle restart between requests; Bazel low-memory exit | Stay alive while connections, pins or waiters exist; idle exit measured, not guessed |

## 3. Priority has to live in the queue, because no one can lift a running process

The servers that stay responsive keep **their own in-process priority queue of small tasks** and do not lean on operating-system priority alone. The cleanest published form is clangd's background index. Each task carries a queue priority, a thread priority, a tag that "allows priority to be boosted later" and a key that drops duplicates. `boost(Tag, NewPriority)` raises every queued task with that tag and re-heapifies, and later tasks with that tag inherit the boost. When the user opens a header, clangd boosts the related files ([Background.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Background.h), [BackgroundQueue.cpp](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/BackgroundQueue.cpp)). The worker thread **sets its own priority per task** before running it and resets it afterwards. A boosted task therefore also *runs* faster, without any process ever being reniced. On Linux, LLVM maps its low and background priorities to `SCHED_IDLE`, and on macOS to the utility and background QoS classes ([Threading.inc](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Support/Unix/Threading.inc)). clangd also ships a switch that "disables thread priority lowering to ensure progress on loaded systems". Its authors know that idle-class work can starve, which supports the budget's guaranteed background share over pure idle priority.

The other responsive designs preempt instead of boosting. Sorbet's fast requests preempt the whole-program typecheck, and Sorbet keeps a **second worker pool reserved for preempting work** because the main pool is suspended during preemption ([LSPTypecheckerCoordinator.h](https://github.com/sorbet/sorbet/blob/master/main/lsp/LSPTypecheckerCoordinator.h)). In IntelliJ, a write action cancels running read actions, which must check for cancellation often ([IntelliJ threading model](https://plugins.jetbrains.com/docs/intellij/threading-model.html)). rust-analyzer cancels stale computations by bumping a revision, and tags every thread with an intent that maps to a macOS QoS class ([architecture](https://rust-analyzer.github.io/book/contributing/architecture.html), [intent.rs](https://github.com/rust-lang/rust-analyzer/blob/master/crates/stdx/src/thread/intent.rs)). Build engines mostly prioritise at admission. Remote execution serves priority levels first come, first served within a level ([EngFlow](https://docs.engflow.com/re/client/remote-execution-priority.html)). Bazel's dynamic execution reportedly hands out local resources newest first, then switches to oldest first past an age threshold so stalled work cannot starve. That comes from search summaries of [Bazel commit 0bae75d](https://bazel.googlesource.com/bazel/+/0bae75d6382cbaf7303ba213b72d4e69db027216) and needs confirming before it is relied on.

This is why the budget design's limit is real, and also why a shared Graph instance can get past it. Apple resolves priority inversions automatically only for waits through serial dispatch queues and mutexes ([Apple QoS guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/PrioritizeWorkWithQoS.html)). A wait over a Unix socket on a key claim is invisible to that machinery. Linux lets an unprivileged thread move *itself* from `SCHED_IDLE` back to normal scheduling, within `RLIMIT_NICE` ([sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)), and macOS threads set their own QoS. **A process can promote its own work, but another process cannot.** As long as commit preparation's Graph work runs as an opaque background child, a review that needs one of its leads can only wait at efficiency-core speed or compute the lead again. If instead commit preparation submits per-hunk lead searches as small keyed tasks into the Graph instance's queue, tagged by store, base tree and lead key, a review that asks for the same key joins it and boosts the tag. Everything not yet started then runs at the interactive class, and only the task already running finishes at its old class. The smaller the tasks, the smaller that leftover delay. The instance itself must therefore start at the default class and lower work per task, never inherit `taskpolicy -b`. Go cannot set per-goroutine priority, so Graph would carry the class to each `git` child it starts per task, or pin tasks to OS threads. That is an inference that has not been tested.

Cancellation and deduplication change meaning once work is shared. LSP requires that "a request that got canceled still needs to return from the server and send a response back". It separates a client's cancellation from content modified underneath the request, and lets partial results stream ahead of an empty final response, which a cancelled client may use if it flags them incomplete ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)). Go's `singleflight` gives every concurrent caller one execution and the same result, but it ties that execution to the first caller ([singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight)). If the first caller's context is cancelled, everyone waiting gets the cancellation. Graph needs the variant that clangd's keys and Buck2's per-key DICE tasks point towards ([Modern DICE](https://buck2.build/docs/insights_and_knowledge/modern_dice/)). The computation runs under a server-owned context, counts its waiters, takes the **highest priority among them** and is cancelled only when the last interested caller leaves. Commit preparation's interest counts as a waiter so its stored answer still lands. DataLoader's batching window, which coalesces all loads issued "within a single frame of execution", is the shape that turns many concurrent searches at one base tree into a single pass over that tree ([DataLoader](https://github.com/graphql/dataloader/blob/main/README.md)). Anthropic notes that Claude's parallel tool calls "can even bottleneck system performance" ([prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)), so parallel `graph_search` calls from several agents arrive in exactly the bursts that batching rewards. No vendor documents batching agents' code-search queries on the server side, so this part is Neuve's own design inference.

## 4. Precompute per blob for every commit, but per base only for a few

No system surveyed prepares a whole-tree artefact for every commit's parent, which is what Neuve's snapshot cache does today. They all split the work in two. One part is **independent of the base and keyed by content**, and it is done eagerly per file or blob. The other **depends on the base**, and it is done for very few commits or left to query time. GitHub's stack graphs analyse each file "completely in isolation", skip already-seen file versions "using only the blob identifiers provided by git", and precompute per-file partial paths so that queries only stitch them together. The authors reject whole-program delta updates because storing per-commit copies of each file's subgraph "would be prohibitive", and they decline to precompute "for a repository or commit that will never be viewed" ([stack graphs paper](https://arxiv.org/abs/2211.01224)). Zoekt indexes only each repository's default branch and leaves other branches to an unindexed searcher, because indexing every branch "isn't a pragmatic use of resources" ([Sourcegraph architecture](https://sourcegraph.com/docs/admin/architecture)). CodeQL builds an overlay base "on your default or long-lived target branch after each merge". Pull-request runs then download the most recent base and analyse only files whose object ids differ, and "any overlay-base database will work regardless of age, but fresher bases produce faster and more accurate results" ([CodeQL incremental analysis](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/scan-from-the-command-line/incremental-analysis)). Sourcegraph moved "which index answers commit C" to write time. It stores, for each commit without data, a link to the nearest ancestor that has it, and over 80% of commits can link that way ([Fritz, Part 2](https://sourcegraph.com/blog/optimizing-a-code-intel-commit-graph-part-2) (the original page no longer loads; read from a mirror)).

**Bursts are coalesced to the newest state.** Zoekt's index server keeps one queue entry per repository and overwrites its options in place, so intermediate states are never indexed ([queue.go](https://github.com/sourcegraph/zoekt/blob/main/cmd/zoekt-sourcegraph-indexserver/queue.go)). Codespaces prebuilds run one workflow per configuration; when it finishes, "earlier pending runs are canceled, and the most recently queued run executes" ([Codespaces prebuilds](https://docs.github.com/en/codespaces/prebuilding-your-codespaces/about-github-codespaces-prebuilds)). Actions concurrency groups allow one running and one pending run ([Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)). Sourcegraph's dirty and update token pair lets uploads that arrive during a recompute leave the repository dirty for the next pass, with no race. The same redesign cut one customer's commit-graph recompute from **5 hours and 21 GB to 5 seconds and about 1 GB** ([Fritz, Part 2](https://sourcegraph.com/blog/optimizing-a-code-intel-commit-graph-part-2) (the original page no longer loads; read from a mirror)). rust-analyzer's cache priming does the unblocking work first, primes symbols only for workspace crates, and aborts itself on any new revision ([prime_caches.rs](https://rust-lang.github.io/rust-analyzer/src/ide_db/prime_caches.rs.html)). A rebase rewrites many commits but creates few new blobs. So per-blob work for its intermediate commits is nearly free, and only the newest tip's work that depends on a base is worth doing.

The strongest outcome evidence concerns **timing, not CPU**. Meta's Infer had a fix rate "near zero" for nightly batch reports, which "rocketed to over 70%" once the same analysis reported at diff time ([CACM 2019](https://cacm.acm.org/magazines/2019/8/238344-scaling-static-analyses-at-facebook/pdf)). The closest external comparator to Neuve's 2–3 minute review target is Greptile, which builds its repository graph at signup and queries it per review ([Greptile docs](https://www.greptile.com/docs/how-greptile-works/graph-based-codebase-context)). CodeRabbit rebuilds its dependency graph for every review, which it can afford with reviews that take 10–20 minutes on cloud instances ([Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/how-coderabbit-built-its-ai-code-review-agent-with-google-cloud-run)). The evidence on what Graph adds argues for keeping it as enrichment. LocAgent's ablation loses about 19 points of file accuracy without keyword entity search but only about 2 without graph traversal ([LocAgent](https://arxiv.org/html/2503.09089v1)). Neuve's own check found lead misses of 0.463 with Graph against 0.467 without ([research 06](06-local-search-under-a-machine-budget.md)). Graph's answers are worth having ready. They are not worth a review waiting 11 s or more for each one.

For Neuve, three conclusions follow. First, the bases to prepare whole are the ones a review starts from: the upstream branch's head and each active branch's merge base with it, in addition to the commit's parent that the current code uses. Second, a lead computed at the parent stays valid for a multi-commit review base wherever every blob its answer depends on has the same object id at that base, which is the same check CodeQL applies. Third, the system should reconcile declaratively, as Zoekt's index server does when it "will compare what Sourcegraph wants indexed... to what is already indexed on disk" ([life of a search query](https://docs-legacy.sourcegraph.com/dev/architecture/life-of-a-search-query)). It should not react to each commit event. When a precomputed answer is missing at query time, none of these systems blocks. They serve the nearest prepared state and mark it stale (Sourcegraph), run a slower path in parallel (Sourcegraph's searcher), or fall back to a full analysis (CodeQL).

## 5. Content keys make sharing safe, and pins plus a size cap keep the disk bounded

Mature local caches make concurrent writes safe **without locks**, through content addressing and atomic renames. Bazel writes to a temporary file, fsyncs it and renames it into place, and states that "concurrent Bazel processes can safely retrieve and store entries in a shared disk cache, even when they collide" ([DiskCacheClient.java](https://raw.githubusercontent.com/bazelbuild/bazel/master/src/main/java/com/google/devtools/build/lib/remote/disk/DiskCacheClient.java)). Go's cache coordinates through file locks and "may duplicate effort but will not corrupt the cache" ([cache.go](https://raw.githubusercontent.com/golang/go/master/src/cmd/go/internal/cache/cache.go)). Deduplicating in-flight work across processes exists only where a single daemon owns the work (sccache, Buck2) or where a lock is taken per key. Nix takes a lock per store path, re-checks the store once it holds the lock, and detects "a lock on a deleted file" ([pathlocks.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/unix/pathlocks.cc)). That is the same shape as decision 10.94's "waiter woken, reads the stored result". With one Graph instance per machine, **every Graph computation runs in one process**, so deduplicating Graph's own keys becomes an in-process single flight, as in gopls and Buck2. The budget host's claims then remain for harness-level records, such as a hunk's stored leads in Records. Commit preparation no longer holds a grant while Graph works, because the Graph instance holds the grants. The rule that work holding a grant never waits on a key therefore stops forcing commit preparation to skip keys a review holds.

Bounds on disk follow two triggers that appear together again and again: an **age rule run at most daily or when idle, plus a size cap that deletes the oldest first**. Go trims entries unused for five days and has no size cap. Its maintainers concede "we ought to have a smarter eviction policy that takes cache size and free space into account" ([golang/go#31931](https://github.com/golang/go/issues/31931)). ccache defaults to 5 GiB and sccache to 10 GB ([ccache manual](https://ccache.dev/manual/latest.html), [sccache Local.md](https://raw.githubusercontent.com/mozilla/sccache/main/docs/Local.md)). Bazel's disk-cache GC shipped in 8.0 after six years and runs only while idle between builds, because online collection with "multiple Bazel processes" sharing one cache was "extremely challenging" ([bazel#5139](https://github.com/bazelbuild/bazel/issues/5139)). BuildKit is the closest fit for a tight Mac disk. Its rules run most specific first (local sources and cache mounts older than 48 h, then anything unused for 60 days, then everything above the cap), and it adds a reserved-space and minimum-free-space floor ([Docker build GC](https://docs.docker.com/build/cache/garbage-collection/)). Last use must not be read from atime, which is coarse under Linux's `relatime` and may not update on APFS ([mount(8)](https://man7.org/linux/man-pages/man8/mount.8.html), [Eclectic Light](https://eclecticlight.co/2025/10/24/be-careful-when-interpreting-apfs-timestamps/)). Cargo records last use in SQLite ([Rust blog](https://blog.rust-lang.org/2023/12/11/cargo-cache-cleaning/)), and Go touches mtime at most once an hour.

**In-use protection is either a live reference or a root that the collector walks.** Nix gives each process a temp-roots file held under a lock, so a file the collector *can* lock is stale. A client that adds a root during collection hands the path to the collector over a socket and waits ([gc.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/gc.cc)). BuildKit only prunes records with no active refs, and locks candidates and marks them dead before removing them ([manager.go](https://raw.githubusercontent.com/moby/buildkit/master/cache/manager.go)). containerd's leases expire after 24 hours "in case the process dies before defer" ([containerd GC](https://raw.githubusercontent.com/containerd/containerd/main/docs/garbage-collection.md)). Sourcegraph's retention ladder keeps the default branch's head forever, branch tips for three months and tags for a year, and never deletes data another index references ([Sourcegraph retention](https://4.5.sourcegraph.com/code_navigation/how-to/configure_data_retention)). Versioned directory names make upgrades clean. Zoekt puts the shard format version in the filename and moves unwanted shards to a trash folder that it deletes after 24 hours ([Zoekt design](https://raw.githubusercontent.com/sourcegraph/zoekt/main/doc/design.md), [cleanup.go](https://raw.githubusercontent.com/sourcegraph/zoekt/main/cmd/zoekt-sourcegraph-indexserver/cleanup.go)). On disk, Zoekt's index runs to about **3.5 times the corpus** for each indexed tree, so the Zoekt index that decision 10.108 puts into Graph's snapshot makes "a snapshot per commit's parent with no eviction" untenable. Any cap has to be set against the number of indexed trees, not the number of commits.

## 6. What Neuve should change, ranked

The ranking puts first what removes the most review waiting for the least build. Where a row needs work on both sides, the harness's half and the instance's half are named apart. Expected effects are inferences from the sources above and Neuve's own figures, and they still have to be shown by the spans each row lists, as decision 10.97 requires.

| Rank | Change | Harness side | Graph instance side | Removes |
| --- | --- | --- | --- | --- |
| 1 | No review waits on Graph without a bound | Read stored leads first. On a miss, join the in-flight key with a short wait, then fall back to BM25 or "no Graph lead", disclosed. `graph_search` returns what is ready, or a pending handle that a later turn or the synthesis picks up | Answer "ready", "in flight (joined)" or "not prepared" at once; always send a final response | Graph in the agent's serial path (Cognition, LSP, Sourcegraph's stale serving) |
| 2 | One instance, one client path for all three callers | Replace the per-process slot, the `graph` and `graph-commit` folders and spawn-per-search with one connection. Each request carries store, base tree, query hash, Graph build id, class, deadline and caller kind. Keep today's per-search process as the disclosed fallback | Per-user address keyed by build id, outside `$TMPDIR` and allowed in sandboxes; elected by a lock before bind; exact version check; prepares by explicit commit, not by moving a shared clone's HEAD, so one clone serves every caller | Duplicate clones, snapshots and computations across processes |
| 3 | Single flight with waiter counts and inherited priority | Ask for a key you need even if background holds it; commit preparation's interest is itself a waiter | One execution per key under a server-owned context; priority is the highest among its waiters; cancelled only at zero waiters | Recomputing a lead the background is producing; a cancel from one caller killing others' work |
| 4 | A priority queue of small tasks with boost by tag | Submit commit preparation's lead searches as one batch of per-hunk tasks tagged by (store, base tree, lead key), not a sequential loop with a 3-minute cut-off | clangd-style heap with `boost`; a reserved interactive worker set (Sorbet); cooperative yield between tasks; class applied per task at each `git` child; the instance itself at the default class | "A running child keeps its class"; reviews waiting at efficiency-core speed |
| 5 | Batch per base tree into one pass | Send one turn's parallel `graph_search` calls together | Short coalescing window per (store, base tree), merging patterns into one multi-pattern scan or index lookup; remember each blob's answer per pattern (10.108) | N scans of one tree for N concurrent searches |
| 6 | Declarative, coalesced commit preparation for the right bases | Per branch, declare the bases wanted (parent, merge base with upstream, upstream head) and the lead queries. Newest wins: one running and one pending per branch, superseded on amend or rebase. Reuse a parent's lead at the review base when the files it depends on have the same object ids there | Reconcile what is wanted against what is stored; per-blob facts for every commit, whole snapshots only for declared bases, overlays for the rest | Snapshots for every parent; wasted work in rebase bursts |
| 7 | Pins and a bounded disk | Hold a pin on the snapshot a running review reads, over its connection; declare durable roots (queued reviews, active branches' merge bases) from Records | Size cap with a free-space floor; rules most specific first (unpinned, undeclared snapshots older than hours, then oldest first); last use in a database; GC while idle under its own lock; version in directory names; never GC when the host is unreachable | Unbounded snapshot and index growth |
| 8 | Measure the queue, not just the search | Spans for queue wait, joined, boosted, ready versus computed, batch size, fallback with its reason | Report per-request phases (queue, preparation, scan) and cache hits by key kind, and per-run eviction counts and bytes | Guessing which row matters next |

**Rank 1 belongs to the harness and does not wait for the instance.** Neuve's own check shows Graph's leads barely move coverage, and outside latency targets sit two orders of magnitude below Graph's median. A bounded join followed by a disclosed fallback is therefore the cheapest way to stop Graph from setting review time. It matches Sourcegraph's habit of serving stale data or a slower path rather than blocking, and LSP's treatment of incomplete results. **Ranks 2 to 5 are the instance itself.** The instance is only worth building as the place where they hold. A shared process without single flight, a priority queue and batching would add shared fate, gopls's warning, without removing the bottleneck. Having Graph do its own deduplication also removes the hardest case in the budget proposal: a review that cannot promote a background child. The promotion becomes a heap operation inside the one process that runs the work. **Rank 6 is mostly harness policy.** It costs little to state which bases are wanted, and it is the only row that lowers total CPU rather than reordering it. **Rank 7** becomes urgent the moment the Zoekt index lands in snapshots. Idle exit for the instance should follow the budget host's rule, staying alive while grants, claims, pins or waiters are open, plus a measured idle period. gopls's one minute is too short for the gap between a commit and its review, and three hours, as in Bazel and Gradle, conflicts with decision 6.9 unless the owner agrees.

Three points stay open. Nothing read shows how any tool drains an outdated daemon that still has clients in the middle of requests. Bazel and Buck2 kill it, and chg leaves the old server running for its existing connections. A Graph upgrade during a review needs an owner call between those two. Whether Graph, a Go program, can apply a class per task without pinning work to OS threads is untested. The fallback is applying the class at each `git` child it starts. No source gives a hit rate for answers precomputed at commit time. Neuve's count of leads found ready against those computed during the review would be the first published figure.

## 8. Conclusion

The shift is from "how many Graph processes may run" to "who decides what Graph does next". Every system studied that stays responsive under mixed load answers that second question in one in-process queue, keyed by content, with priority attached to queued tasks rather than to processes. Neuve's machine budget rations CPU between processes well, but it stops at the process boundary: it cannot speed up work already running. The one shared Graph instance is the one place where that limit goes away, provided commit preparation hands it fine-grained keyed tasks instead of running as an opaque background child.

The harness's role shrinks to three things: saying what it wants (keys, bases, class, deadline), never waiting on Graph without a bound, and holding what it reads (pins). Everything that makes Graph fast, including deduplication, batching, promotion and eviction, moves behind the instance's boundary, the same way the harness's other callers already reach Graph only through `@neuve/graph-client`. If the first spans show that most leads are found ready and joins are rare, ranks 3 to 5 can be built lean. If joins and boosts dominate, the queue is the product.
