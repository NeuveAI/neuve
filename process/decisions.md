# Design decisions

This is the working source of truth for the correction effort that started on 16 October 2026. The owner states each decision in conversation. The coordinator records it here, compares it with the docs and the code, and notes any conflict. The [architecture records](../architecture/README.md) describe the system that follows from these decisions. The [product vocabulary](../vocabulary.md) and the [foundations](../foundations/) remain authoritative for product meaning. The earlier plans and handovers that these decisions superseded were removed on 16 October 2026. They remain in git history at commit `c8b73b41`, for example `process/dependency-investigation-plan.md`.

Each entry has a date, the decision, and its consequence for the code. Superseded entries are deleted. Git keeps their history.

## Area 1: product loop and roles (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 1.1 | The foundations describe the product loop correctly. Local work is driven by Neuve skills that guide a coding harness (Codex, Claude Code) through the prescribed workflow: planning, then the inner implementer and adversarial-reviewer loop, then a fully independent reviewer. "Start a review" in the web app is a valid trigger but not the primary driver. | The CLI, MCP and ACP connections carry agents' use of Neuve tools into Records, with the identity and markers that attribute their work. The "Start a review" button and web event handling are reported broken; check them as a defect. |
| 1.2 | The first scope is final-review preparation. Records and the CLI must still provide the commands, APIs and tools that collect data for the system of records. The graph must connect to Records for retrieval and for embeddings, the semantic half of the hybrid system. (amended by 14.53) | The inner loop is not built as a product flow now. Its data collection surfaces are. |
| 1.3 | Neuve is a hybrid system, semantic and agentic. The research and transcripts in the repo document this direction. | Do not reduce it to a single retrieval path. |
| 1.4 | A review takes a commit range as input, attributed to a base branch. The range is the fingerprint: git immutability means the same range always carries the same changes, which avoids recomputation and makes Records efficient. | The range, plus the pipeline and configuration that processed it, identifies work and reuse. Area 5 settles the rerun rule. |
| 1.5 | Records follows entire-cli's approach to building a system of records around git, collecting fingerprints and breadcrumbs of agentic work. The local reference is `~/code/.better-coding-agents/resources/entire-cli`, and the research is in [Entire and code context](../research/03-entire-and-code-context.md). | Records stores and attributes the identity of the agents working on a batch. |
| 1.6 | One pipeline gathers data and evidence, runs hybrid retrieval for surrounding context, prepares the package, and produces the agentic review together with pre-generated dispositions for human-suggested and human-required units. Everything lives in the same package. Precomputation may still happen at collection time and in the Records layer. | No separate reviewer session reads the package for the outer agentic review. Precomputed results are reused, not regenerated. |
| 1.7 | The web app is mainly an event-driven interface between Records, the main harness and connected tools, such as ACP. | Business logic does not live in the BFF. The web app projects Records state and relays commands and events. |
| 1.8 | Scope comes from whatever is available: a Linear ticket, a markdown plan, or ad hoc. The pipeline is opinionated, and Neuve skills prescribe it to people who install the CLI. Review context is always gathered from the sources that are available. | Never refuse or stop because a scope source is missing. Disclose the gap and continue. |
| 1.9 | "Frame" is not a product concept. Codex introduced it. The vocabulary's review units, surrounding context and other terms describe the product. The designs in Storybook and the `.pen` file show the concepts and are slightly ahead in some areas. The human reviewer sees only the batch overview and review desk. Inner and outer agentic reviewers drill into the same data through the CLI. | Remove "frame" from product surfaces, prompts and docs. Gathering scope sources is an internal pipeline step with no product name. |
| 1.10 | The full test passes when the owner can open a batch in the review desk and see human-suggested and human-required units with correctly attributed surrounding context, pre-generated dispositions and digests. The quality of each part is improved after one full round works. | This is the exit for the first scope. Quality hill-climbing comes after it. |

## Area 2: harness pipeline (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 2.1 | The harness owns scope gathering, hybrid retrieval with multiple leads, refinement and reranking, deterministic checks, matching units to context, briefings and digests, lanes, and collecting dispositions. This confirms the 13 October clarification. | No separate component takes over any of these. |
| 2.2 | Neuve's own harness owns the final-review pipeline entirely. ACP connections are for live communication with editors and external harnesses (Codex, Claude Code), and only when those are available. The skills from 1.1 drive the inner loop through the local harness. | Final review never depends on an external coding agent being connected. |
| 2.3 | Every stage is hybrid. Retrieval combines semantic and agentic parts, and computation combines procedural or deterministic steps with agent reasoning and tool calling. No single agent drives everything, and no stage is purely scripted when judgement is needed. | Each stage states which parts are code and which are agent reasoning. |
| 2.4 | Avoid one-shot prompts. Understanding the change and its scope sources is a multi-turn step. | Understand and Investigate are both multi-turn agent steps with tools. Neither is a single generation. |
| 2.5 | Budgets are resilient. The pipeline always tries to produce the batch from whatever context it has retrieved. Turn limits for Understand and Investigate, together with good context management (growth control, caching, prompting guidelines), keep cost down. There is no token or dollar cap for now. Cost is tracked per the KPIs. | Exhausting a limit or failing a stage leads to generation from the retained context, never a dead end. Prompt caching and context-growth control are requirements, not optimisations. |
| 2.6 | Retries are part of the harness. Cap them and follow established practice, for example backoff and shrinking context on overflow. Errors will happen. What matters is good error management and proper recovery procedures. | Every model and tool call has a bounded retry policy and a recorded recovery path. |
| 2.7 | Immutability by range. Generations and all computations are saved and reused, never reprocessed for the same range. The harness stores them in a database, and the relevant parts go into the system of records. These may be two sides of one data architecture. | Area 5 settles where storage ends and Records begins, and the rerun rule. |
| 2.8 | Once a unit is attributed to a lane, it contains only its relevant line ranges (hunks) and surrounding context. That context can include some padding and other code parts. | A unit owns ranges, not whole files. Context stays separate from owned work. |
| 2.9 | Model route for the first full round: ACP connected to Codex for Sol 6.1, if it can be set up properly. Otherwise, Opus 5.5 through the Anthropic API integration. | Remove the EVE ChatGPT consumer-backend route. Budgets derive from the chosen route's window. |
| 2.10 | Records connects to Git and is the endpoint for the CLI that the inner loops use. Fingerprint, identify and precompute whatever makes sense as agents record and commit code or other metadata. | Precomputation is attached to agent activity and commits, not run cold at review time. |
| 2.11 | Each route's context window comes from the provider's own metadata. For Sol 6.1 that is Codex's model metadata (`~/.codex/models_cache.json`): 500,000 tokens with 95% usable, about 475,000. Opus 5.5 is 1,000,000 tokens of input and 128,000 of output. The old 272,000 belonged to gpt-6-sol. The 131,072-byte, 64,000-token and 30-second frame limits came from a one-case development envelope and are discarded. | Every stage budget is derived from the route's window and counted in tokens. The EVE ChatGPT route dropped `maxOutputTokens` before sending, so output budgets must be enforced where the route allows it. |
| 2.12 | For M3 the harness is built on Opus 5.5 through the Anthropic API. The ACP harness is kept warm: the ACP client path to Codex stays working, and it switches to Sol 6.1 once a released Codex accepts `gpt-6.1-sol` and a true read-only mode exists (17 October 2026). | M3 implements on Opus. A maintained, runnable ACP path is part of M3, not a later rebuild. |
| 2.13 | Each agent (Understand and Investigate) gets 70 turns. If that proves too few, reconsider or add finer-grained limits (17 October 2026). | This replaces the 50-step limit. The limit applies per agent, not per batch. |
| 2.14 | The harness prompts tell agents not to be long-winded, because verbosity hurts their context. They use as much context as the task needs and no more; when a consideration genuinely needs more, they may use it. Agents must recognise when they are done (17 October 2026). | Prompt guidelines cover concise output, using context as needed, and clear stopping criteria. |
| 2.15 | Agents get a venting tool for recording frustrations and friction in their own words, following [Lovable's vent tool](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool) (17 October 2026). | A `vent` tool is available to harness agents and, through the CLI and MCP, to inner-loop agents. Each vent is a record in Records, attributed to the agent, run and stage. It never changes the task or the review. The prompt shows a few examples of good and bad vents rather than rules. At most one vent per turn (Lovable had an agent send 43 in minutes). Vents are read through the CLI. Triage, clustering and auto-fixes come later. |
| 2.16 | Codebase facts are kept apart from agent session work and artifacts. An agent sees only what its task may see: in the harness, through a separate context; on disk, through a working directory outside the repository (for example under `/tmp`) that holds nothing else. Other agents' outputs, rankings and private records never sit where an agent works (18 October 2026). | Learned from the M4 labelling pilot, where a labeller read retriever ranks and a grader read the labels it was checking because they shared a folder. Applies to the harness and to all future labelling. |

- How bounded per-unit calls in Assemble and Disposition run over ACP, which provides an agent session rather than a single model call.

## Area 3: context and retrieval (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 3.1 | This corrects [the structural-engine foundation](../foundations/09-structural-engine.md). The hybrid approach combines structural analysis, other static and procedural analysis, and agentic analysis. The graph is not solely responsible for structural work. Further research shows graphs serve semantic embedding, analysis and retrieval. The Graph fork may be reset to the entire-graph baseline, and what to use will be reconsidered alongside the EmbeddingGemma 2 fine-tuning. | Foundation 09 needs revision with the owner. Structural and static analysis get their own explicit operations and do not live inside Graph query. |
| 3.2 | The semantic layer finds meaningful leads and carries the metadata needed to refine them. Structural facts come from separate, explicit queries. This confirms the 13 October correction. | Implement structural follow-up, which is hard-coded to "unavailable" today and was never built. |
| 3.3 | Benchmark before committing to a strategy. Compare the fine-tuned EmbeddingGemma 2 against its baseline and other options, using standard practice and the research and transcripts in the repo, then consolidate one strategy for the semantic layer. | No more semantic-layer building until the benchmark exists. The existing research gives the starting point. |
| 3.4 | Graph and embedding entries need provenance metadata so results can be attributed and cited correctly. Retrieval results the package cannot cite are a defect. | Fix citation of Graph and embedding results. The metadata ticket is likely NEU-13, versioned embeddings during ingestion, together with scratchpad notes from about 13 to 14 October. Confirm against Linear. |
| 3.5 | Surrounding context exists only for changed lines. It may relate to other parts of the codebase, but its anchor is always a changed line in the unit. | Every context reference has an L0 anchor on a changed line. Pins for retrieved context attach there. |
| 3.6 | The semantic layer (graph and embeddings) indexes code and local docs. Scope sources (when available), prior Records reviews and comments, and git history enrich and rerank results in procedural collection. The agentic layer then refines, reranks and prunes context down to what matters for the review and for future generations. | Retrieval is semantic first, then procedural enrichment, then agentic refinement. The agent may prune. |
| 3.7 | Build and test order: pass 1 is semantic, then scope sources, then agentic. Pass 2 is semantic, then scope sources, prior Records, git history and static analysis, then agentic. Running two passes measures how much the extra context actually helps. | Build pass 1 first and measure. Pass 2 adds the remaining sources, and its value is measured against pass 1. |
| 3.8 | Separate indexes queried individually are the likely first-build path. They are easier than one central graph answering a single "omni" query. Signal-to-noise decides which to use. | Keep code, docs and other sources queryable separately, then merge and rerank. |
| 3.9 | The index follows Entire's approach as a product: use git as the guide and update the graph as code evolves. Hash metadata supports searching by range. | Index incrementally from commits. Ranges resolve through hash metadata. |
| 3.10 | Adopt one context-reference contract, specified in detail for each architecture layer. | Specify the contract across the semantic layer, Records, the package, the CLI and the BFF before implementing it. |
| 3.11 | The context margin layers, checked against Storybook on 16 October. **L0 pin:** kind icon and label, count, shared-unit dots. **L1 peek:** one row per marker on the line, showing kind, one-line why, and source and revision meta. **L2 card:** kind header, title, kind-specific body (for example a graph tree with hop depth and revision), "Before you decide" with one sentence and one action, and Open source. **L3 source sheet:** kind, committed or same-batch flag, revision, title, kind-specific content and coverage, and the units citing it. | The contract in 3.10 must supply every field these layers show. |
| 3.12 | External process systems (Linear, Notion, Jira and the like) are a main scope source, because teams keep process there. Neuve keeps no standing local copy. It fetches from them at the start of every cycle, for the inner loop and for the cycle's final review. Neuve keeps only the excerpts that enter a unit's surrounding context, each with the date and time it was fetched; everything else in the fetched item is linked, not stored. Those excerpts become part of the batch's and cycle's immutable data and follow the same retention as that data. A citation links to the source item and says the excerpt was taken on that date. This grounds every generation in the truth available at the time and avoids drift (17 October 2026). | Applies 5.4 and 8.10: generations in a cycle use only that cycle's snapshot, and fetching again is a new snapshot in a new cycle, never a silent update. |

## Area 4: units, lanes and dispositions (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 4.1 | Review units are always grouped by filename and proximity. Batches are grouped by behaviour and obligation, which supports digests and a cohesive review. The Storybook batch overview shows one batch: one behaviour ("Revoked share links stop working immediately", SHR-212, its branch and commit) containing 26 units. Each unit has a behaviour label and its scope in files and hunks. | The agent does not regroup units by behaviour. Behaviour and obligation decide the batch. Units are a code-proximity grouping within it. |
| 4.2 | Lanes come from assessing where each unit falls on a complexity × ease-of-validation matrix. History, prior bugs, outages and blast radius can move a unit. The starting quadrants are: low complexity and easy to validate → static automation or agentic; low complexity and hard to validate → human-suggested; high complexity and easy to validate → agentic or human-suggested; high complexity and hard to validate → human-required. | Add a typed per-unit assessment (both axes, cited evidence, quadrant, lane, rationale) in the package. Code maps the quadrant to a lane. The rationale reaches the UI. |
| 4.3 | The static automation lane is assessed against validation requirements, because each one fulfils the other. A unit qualifies when its validation requirements are met by checks. | Static automation depends on mapping validation requirements to checks, as the batch overview's Verification section shows (missing, shallow, solid). |
| 4.4 | Assessment is always best effort. If gaps prevent a confident assessment, the unit goes to human-suggested, not human-required. A best-effort assignment needs no special label (amended by 14.4). | Gaps never block a unit or the package, and a best-effort lane is not flagged. |
| 4.5 | Pre-generated dispositions: the agent approves or requests changes on agentic and human-suggested units. On human-required units it writes a suggested review and comments, and never approves. It may request changes on any lane. | Implement suggested review, which exists only in fixtures today. |
| 4.6 | Human-required units also get suggestions and comments. The review delivery dial (Facts, Briefed, Explained, Guided) needs generated content for each stop in this mode as well (amended by 14.4). | The pipeline generates the content for each delivery stop, not just one briefing. |
| 4.7 | A new disposition runs in a fresh context, but only after the whole batch has its dispositions. | Coordinator's reading, to confirm: the pipeline first produces dispositions for the whole batch. Any later disposition, such as a re-review after comments or changes, starts from a fresh context reading the frozen package. |
| 4.8 | Digests: the batch overview has a batch digest (the hero briefing, "Advisory briefing · no decision required"). The desk has a digest for each unit, a contextual briefing with phrase links and citation chips (Conflict, Gap, Same batch). The desk's context is narrower: one unit within a batch grouped by behaviour or obligation. | The batch digest is the isolated briefing and the unit digest is the contextual briefing, both confirmed against Storybook. "Digest" can link to those vocabulary terms. |
| 4.9 | The owner expects a lot of alignment work here. No quadrant exists in code, suggested review is fixture-only, units stopped by gaps never reach a human, and the static automation lane can't be completed. | These are the main implementation gaps for Area 4. |
| 4.10 | One commit range can produce several batches, one for each behaviour or obligation, so each review has a single area of focus. | The pipeline splits a range into batches by behaviour or obligation, then groups each batch's units by file and proximity. |
| 4.11 | The coordinator's reading of 4.7 is confirmed, and the owner defines a review cycle. A cycle runs: scope gathering for the inner loop, then the inner loop (implementer and reviewer), then the harness pipeline, then review. Gathering every needed disposition ends the cycle; comments do not. When the outer reviewers (human, agent or both) finish their dispositions, either approval or request for changes with comments, the cycle ends and a new one begins. Approvals can carry comments, which feed into the next cycle as context. | This refines the vocabulary's "review cycle" entry. The coordinator will propose the wording for owner approval and will not edit the vocabulary unilaterally. Dispositions are stored for later reference and never regenerated. |
| 4.12 | Ranges vary. A reviewer may need to check ranges outside the base, or ahead of it to narrow the scope (17 October 2026). | Same-batch context is work inside the selected range. Work outside it is context carrying its own review status, such as reviewed in an earlier cycle or not yet reviewed. Range selection is part of the review request. |
| 4.13 | When a unit's lane changes to human-required after an agent has already approved it, or an agent approved before any assessment, that earlier disposition no longer closes the unit. History keeps it, and pre-recorded dispositions become part of the unit's context. The unit escalates to the human reviewer with what was recorded. There is no separate "no longer counts" state: states and labels on context are for classification and ownership (17 October 2026). | Whether the needed dispositions are in is judged against each unit's current lane. Earlier dispositions reach the human reviewer as context items. |
| 4.14 | An agent's request for changes on a human-required unit does not close it. Only a human's disposition closes human-required work. The agent's request for changes reaches the human as a pre-recorded disposition in the unit's context, and the human decides whether to send the work back (17 October 2026). | Applies 4.13 to both verdicts. 4.5 still lets agents request changes on any lane. |

## Area 5: system of records (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 5.1 | The base layers are the harness, the system of records, MCP, the graph, the CLI and the web app. Each has its own internal abstractions and needs proper layering. | Records stores and coordinates. The harness runs pipeline and model work as a client of Records. Model calls, the ACP relay and finalization move out of the Records process. |
| 5.2 | The system is fully event-driven. Any additive work, whether creating records or editing them, runs as a background process. Commit immutability allows computations such as embeddings to be produced in the background. | Records emits events, and background workers do the precomputation (2.10). |
| 5.3 | Two kinds of persistence. A computation store, addressed by a hash of each input, holds generations, tool results, embeddings and large blobs. Records holds the events: batches, units, context references, assessments, dispositions, comments, and agent identity and activity. Records reference computations and do not copy them. Every finished computation goes to its persistence layer. | Persistence abstractions cover both the filesystem and the database. |
| 5.4 | Never recompute. A query or rerun for a range that is already computed makes no new computation. On a partial hit, use as much of the cache as possible, but surrounding context may still need reranking, or refinement through new queries. Reruns and retries use as many cached computations as possible. | Cache lookup happens per computation, not per whole run. Partial reuse is normal, and context assembly can rerank over cached and new results together. |
| 5.5 | The prepared snapshot can be transient, existing for the review cycle. Persistence must scale: no duplicated events, no copy of the state stored per change, and data that can be pruned and refined. The current design (2,571 full snapshots, 13.62 GB against 25 MB of records, each event written about 16 times, transcripts embedded in the state) is rejected. | Records become the truth, and projections are rebuilt from them. Each event is recorded once. Transcripts become referenced blobs. Fix the lease self-lockout bug. |
| 5.6 | Consider Entire's model of storing records in git refs outside branch history, instead of a `.neuve` folder. The owner asks for a design exercise on how that would look. | This is a design exercise before the Records persistence layout is chosen. |
| 5.7 | Records captures any valid telemetry and identification metadata for agents. Forking entire-cli and basing the CLI on parts of it is acceptable. "Basing" is the operative word: Neuve's product principles come first, and only the parts that fit are used. | Records adopts entire-cli patterns where they fit, without its model replacing Neuve's. |
| 5.8 | Raw session transcripts and large tool outputs are saved, with at most 30 days of retention for full session data. | Add a retention job. Durable records and their references outlive the raw session data. |
| 5.9 | Zod is the schema library. Effect can consume zod schemas. | Remove duplicate Effect Schema definitions of domain types and derive them from zod. |
| 5.10 | Prune now: archive the full ledger snapshots, the backup and the untracked copies outside the repo, then delete them. Scratchpads stay. | Archive before deleting, with the exact list confirmed by the owner first. |


## Area 6: runtime and platform (16 October 2026)

| # | Decision | Consequence for the code |
| --- | --- | --- |
| 6.1 | No dependency patches. Remove `patches/eve@0.70.2.patch` and `patches/@tanstack%2Frouter-core@1.171.32.patch`, assess why each exists, and find a proper replacement. | Fix the router patch by pinning versions or upgrading. The EVE patch goes away with the runtime decision in 6.2. |
| 6.2 | Don't hand-roll a harness on the raw AI SDK. Either lean on EVE, which provides hooks, memory, sandbox, ACP, evals and AI SDK support, or find a suitable replacement. The owner is open to suggestions. Effect is the core philosophy and dependency everywhere except the web frontend, where TanStack Start uses Effect in the BFF and the pieces connecting to the backend. A state-machine option may help code the workflow. | Open: choose the harness runtime. See the open items below. |
| 6.3 | The harness can run as a long-running background process, which suits the event-driven design. The CLI install needs a proper macOS background-service integration. | Open: whether to run a long-lived service or an on-demand worker. See the open items below. |
| 6.4 | MCP over stdio if the harness runtime allows it. EVE accepts only Streamable HTTP or SSE. | The MCP lifecycle follows from 6.2. |
| 6.5 | An official release pipeline: a binary distribution with its modules, installed on the PATH and upgradeable. The final distribution must be tested. A single local-development launch command is fine for development. | Tests and development never touch the installed binary. The release build is what end-to-end tests exercise. |
| 6.6 | No auth or authorization code on Neuve's side. Git credentials are enough. Agents have their own sessions in the external harness and provide a fingerprint, and Neuve gives agents aliases based on those fingerprints. | Remove all tokens and credential checks. Actor identity becomes fingerprint plus alias, used for attribution only. |
| 6.7 | Not precious about the current Records data. Nobody uses it and it is in active development. | The live ledger was archived and deleted along with the other pruned items (5.10). |
| 6.8 | The harness runtime is Effect-native: `effect/ai` (LanguageModel, Chat, Toolkit, Tokenizer, EmbeddingModel, Telemetry, McpServer with a stdio layer) and `effect/workflow` (Workflow, Activity, DurableQueue, DurableClock, WorkflowEngine), plus an ACP client to codex-acp for Sol. These primitives must serve the durability and state-machine needs and the event-driven architecture. EVE leaves the harness, and its patch goes with it. | A short spike first confirms three things: an Anthropic provider for Effect 4, an ACP client tool loop against codex-acp, and workflow resume under Bun. MCP runs over stdio. |
| 6.9 | Process lifecycle follows Entire. Hooks record events quickly, the events queue background jobs, and a worker starts when work is queued and exits when idle. The release install also registers a macOS launchd agent, so queued jobs are picked up without a hook firing. There is no always-on service. | Capture stays fast and synchronous. Long jobs (embeddings, pipeline runs) run in the on-demand worker. |
| 6.10 | Neuve's work must never be unbounded on any machine, local or hosted: unbounded CPU work saturates any machine and risks crashes and a bad experience. Ingestion and indexing run progressively rather than as one CPU-bound burst, with bounded concurrency everywhere. Noted on 17 October 2026, when the benchmark's Graph queries ran `git grep` at about 700% CPU alongside two embedding processes; responsiveness held, so this is a design requirement to keep in mind, not an emergency. | Candidates when it is designed: lower worker priority, bounded concurrency and thread counts for git and encoders, incremental ingestion as commits land (3.9), and pausing heavy jobs when the machine is busy. The benchmark itself may run on Modal. |

## Area 7: how agents build Neuve (16 October 2026)

| # | Decision | Consequence for the work |
| --- | --- | --- |
| 7.1 | Each lane has one implementer and one independent reviewer. An overseer reviews only at milestones. Reviews are time-boxed to about 30 minutes, and only correctness or security defects block; evidence gaps become follow-ups. The reviewer needs real independence: its own goal, sharing only the task's definition of done and scope. It must be properly adversarial and skeptical of everything (amended by 14.9). | The reviewer's brief contains the shared DoD and scope, never the implementer's own account as a premise.
