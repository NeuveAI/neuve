# Sessions in Ace: proposal

Status: proposal, drafted 23 November 2026; the owner ruled on commit attribution and Ace's Codex hooks the same day. Nothing here is built. It designs how Neuve, inside Ace, gets what it needs about agent sessions from Ace's own records instead of from capture hooks. The [decisions record](../decisions.md) wins wherever this text differs from it. Code was read at `97c8b54`, and at `f1db36e` for the ruling's sections; no program was run to write this.

> "once in Ace, neuve does not have to capture sessions as ace will have it all. We will have same as t3code and opencode, all session information (toolcalls, messages, results) in the main session channel or threads. Neuve can just tap into it as it is, or will be, deeply integrated. So, standalone neuve...sure, but neuve in ace will not do that."
>
> The owner, 21 November 2026, recorded as [decision 14.80](../decisions.md#area-14-lane-assignment-and-agent-dispositions-redesigned-12-november-2026), which adds, on recovering what capture missed: "no backfill, please...don't overthink"

**Words.** _Capture_ here means what `neuve setup hooks` installs: agent hooks in the person's Claude Code and Codex configuration, and Git hooks in the repository. _Standalone_ means a person running Claude Code or Codex directly, outside Ace. An _agent session_ is one run of such a program as capture records it. _Chat_ is Ace's implementation word for one conversation of a channel, whether a person writes in it (a [thread](../../vocabulary.md#comments-and-threads)) or an agent works in it (a subagent, or a plan's agent read on the work log). Capture, standalone, agent session and chat are not in the [vocabulary](../../vocabulary.md), and are listed for the owner under [Still open](#still-open-for-the-owner).

## At a glance

```
 STANDALONE (unchanged)                        IN ACE (proposed)
 ──────────────────────                        ─────────────────
 Claude Code or Codex                          Ace chat on pi, Claude Code or Codex
   │ agent hooks                                 │ Ace keeps every message, tool call, result,
   ▼                                             │ model and usage in the channel's store
 spool, then worker, into the                    ▼
 repository's Records: session,                channel worker retires: Neuve's workspace files
 turns, transcript, tokens                     a session dump (built today)

 git commit                                    git commit from a chat's shell
   │ post-commit hook                            │ the same post-commit hook, still the one writer
   ▼                                             ▼
 actor = the live session whose                actor = the chat Ace named, or the default
 process is the nearest ancestor               Git user when the person's setting says so

                                               Codex write turn
                                                 │ Ace turns Codex's hooks off
                                                 ▼
                                               records nothing
```

1. **Nothing new copies a session.** Ace already holds each chat's full record, and Neuve's workspace files a session dump of the channel when its worker retires ([`workspace-cli.ts`](../../apps/neuve-cli/src/workspace-cli.ts), lines 472–525). Neuve reads that dump after the run.
2. **Ace's Codex runs without hooks.** A Codex write turn runs on the person's own Codex configuration, whose hooks load ([`PROTOCOL.md`](../../packages/runtime-codex/PROTOCOL.md), line 96), so in a repository set up for capture Neuve's Codex hook could record the chat. The owner ruled that Ace turns those hooks off, as it already does for read-only turns.
3. **Commits stay with the Git hooks.** Ace names the channel and chat, and the hook records the chat as the commit's actor, or the default Git user when the person's setting says so.

## What capture serves today

Agent hooks turn each session and turn edge into events in a spool file and never open SQLite ([`agent-hooks.ts`](../../apps/neuve-cli/src/capture/agent-hooks.ts), lines 159–360; [`hook-cli.ts`](../../apps/neuve-cli/src/capture/hook-cli.ts), lines 34–49). They also keep small live-session files, each naming the agent process that owns the session ([`sessions.ts`](../../packages/records-core/src/sessions.ts), lines 1–30). Git hooks record each commit ([`git-hooks.ts`](../../apps/neuve-cli/src/capture/git-hooks.ts), lines 135–174). A hook acts only where the repository's common Git directory holds `neuve/capture.json` ([`hook-main.ts`](../../apps/neuve-cli/src/hook-main.ts), lines 25–65).

## How Neuve reads them

| Option                                                 | What it costs                                                                | What it breaks                                                                                                                                                                                                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Open `channel.sqlite` from a Neuve process             | A second reader of pi's private schema                                       | The store has one owner, which also holds the credential inspection ([`workspace-cli.ts`](../../apps/neuve-cli/src/workspace-cli.ts), lines 278–352). A live read means polling, which [shared work](../../architecture/decisions/0016-shared-work.md) forbids     |
| Ask the host, live                                     | A subscription per channel and a Records writer for each turn                | Copies every turn into Records beside Ace's own copy, which the pi capture boundary rules out                                                                                                                                                                      |
| Ace writes the hooks' events itself at each turn       | A new writer, and a transcript reader for pi                                 | Two stores of one session. The transcript job reads only the transcript its session named when it started ([`transcripts.ts`](../../packages/records-core/src/transcripts.ts), lines 74–80), so it would need a pi reader too                                      |
| **After the run, from the session dump** (recommended) | Nothing to build for transcripts: the dump is filed today, once per snapshot | Facts arrive when the worker retires, not live. None of the uses above needs them sooner, but a worker that never retires never files its dump, so a channel left running has none until it does. The dump is in the coding store, so the dataset work reads there |

**Recommendation.** Neuve reads Ace's sessions after the run, from the session dump it already files. Live, it needs one thing from Ace and no copies: which channel and chat a process works for, so commits and `neuve` commands are attributed.

## Commit attribution

> "We can setup as such but maybe should expose as a setting option on ace. Some people will prefer to use the default git user."
>
> The owner, 23 November 2026, answering the recommendation to credit a commit to the chat that made it, with the Git hook recording and Ace naming the chat, and to turn hooks off for Ace's Codex.

**Where a commit's author comes from today.** Ace sets no `GIT_AUTHOR_*` or `GIT_COMMITTER_*` variable and no `user.name` or `user.email` for a chat. A pi chat's shell runs in the worker's environment ([`worker.ts`](../../apps/neuve-host/src/worker.ts), lines 100–104), the host's own minus Git's repository-local variables ([`host-config.ts`](../../apps/neuve-host/src/host-config.ts), lines 32–48 and 78–79). So Git resolves the author and committer as in the person's terminal: the repository's config, shared by all its worktrees, then the person's global config. That pair is the default Git user: asked on 23 November 2026 what it means, the owner said "as in whatever is configured on git config" ([decisions record](../decisions.md#area-17-the-owners-rulings-on-returning-23-november-2026)). On this machine only, this clone's unversioned `.git/config` names Neuve, so an Ace chat's commit here is authored by Neuve. A teammate's clone sets no identity unless they set one, so their commits carry their global one.

Records takes the actor from the `post-commit` hook in the repository's common hooks folder ([`setup-hooks.ts`](../../apps/neuve-cli/src/capture/setup-hooks.ts), lines 693–696); a lane is a worktree of that repository ([`lanes.ts`](../../packages/channel/src/lanes.ts), lines 150–170). No live session owns Ace's processes, so, reasoned from the code and not run, the hook records the default Git user, by email, as the actor of an Ace chat's commit ([`git-hooks.ts`](../../apps/neuve-cli/src/capture/git-hooks.ts), lines 93–113). If the host was started inside a standalone Claude Code or Codex session, ancestry reaches that session instead.

**Decided: the Git hook records, and Ace names the chat.** Each channel worker writes a live-session file for the channel, owned by the worker's process, in the folder hooks use for live sessions ([`sessions.ts`](../../packages/records-core/src/sessions.ts), lines 23–30 and 200–215), and removes it when it closes. Ace also sets a variable naming the channel and chat in each shell and runtime process it starts for a chat, and caller resolution takes the chat from it only when it names a chat of the channel ancestry found. A variable inherited from another channel is ignored. The link is `ancestry`, which [the commit schema](../../packages/records-schema/src/events.ts) (lines 1705–1738) already allows, and the hook stays the one writer. Ancestry comes first, as the [declared-link decision 8.13](../decisions.md#area-8-records-rebuild-m2-17-october-2026) requires, so a standalone agent started from an Ace chat's shell, a nearer ancestor, keeps its own commits.

**The setting, in its smallest form.** This is assumed from the owner's words; what it leaves is under [Still open](#still-open-for-the-owner). Ace never writes Git's author or committer; they stay the default Git user, and only the actor in Records changes. One setting chooses whether a chat's commits go to the chat or to the default Git user. It is saved with the host's other preferences in its `settings.json` ([`preferences.ts`](../../apps/neuve-host/src/preferences.ts), lines 17–76) through the existing `preferences` request ([`gateway.ts`](../../apps/neuve-host/src/gateway.ts), lines 724–728), and shown in the General section of Ace's Settings beside Projects and Models ([`settings.tsx`](../../apps/app/src/settings.tsx), lines 519–546). The worker copies it into the channel's live-session file when it starts, where the hook reads it; a change reaches a channel when its worker next starts. On the default Git user, the hook records the commit as it does with no session: the committer is the actor and the link is `none`. Proofs, vents and requesters from the chat stay linked to the chat either way.

**Known limits.** A chat whose shell commits in a second repository leaves no channel file in that repository's store, so those commits go to the default Git user, as today. A shell that cannot read the process table, as the commit schema says agent sandboxes may forbid ([`events.ts`](../../packages/records-schema/src/events.ts), lines 1705–1715), cannot reach the worker. Codex sets `CODEX_THREAD_ID` in its shells; with its hooks off in Ace that thread names no live session, so the declared rule picks nothing ([`caller.ts`](../../packages/records-core/src/caller.ts), lines 108–141) and such a commit comes out unresolved, as today. A Codex write turn cannot commit in a lane at all today: the chat's folder is its only writable folder ([`launch.ts`](../../packages/runtime-codex/src/launch.ts), lines 164–171, the mode table that sets what a turn may write), a lane's commit writes into the main checkout's Git folder, and Codex's sandbox refuses that write. A lane observed the refusal on 23 November; its notes are not recorded in this repository. How Codex agents get to commit is the owner's to decide.
