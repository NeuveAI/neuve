# Agents in shared channels: proposal

Status: proposal, drafted 23 November 2026 from the owner's conversation with the coordinator that day, revised the same day for the owner's eighth answer, and on 24 November for the ninth, tenth and eleventh. On 25 November it gained [Making an isolate fast and keeping the host lean](#making-an-isolate-fast-and-keeping-the-host-lean), for the owner's questions on speed, teardown and shared resources, and the owner's choice of an APFS disk image for sandbox storage (row 17.53). The same day, the owner ruled that every channel's agents run in isolates from the start (row 17.55). Nothing here is built. The owner's first answer accepted the narrow folders, the seventh decides where the reviewer's behaviour lives, the eighth decides where a shared channel's agents run, and the ninth gives each agent an isolate that is a micro-VM and asks for its teardown, and the tenth accepts the recommendations on which micro-VM and on when an agent is done; the rest is proposed. The [decisions record](../decisions.md) wins wherever this text differs from it. Code was read at `f1db36e`, and for the section on making an isolate fast at `a8fae1c`. For the ninth answer, two clones of this repository were timed on the owner's Mac; for that section, copies, clones, reads and deletes were timed on the LaCie drive on 25 November; nothing else was run.

**What is decided.**

1. A shared channel's agent loop, its tools and its durable session run inside the channel's shared sandbox on the tailnet. Model calls and Git pushes leave through the broker, which swaps in the key or token on the way out, so no credential enters the sandbox. Neuve's own steps (the scope read and reviews) run outside with the Records store and read the branch the broker pushes.
2. Inside that sandbox each agent has an isolate of its own: its own clone, which it owns entirely. Only a branch leaves, with its proof. Each isolate is a micro-VM, so that agents do not load the host machine.
3. An agent's isolate is torn down and cleaned up when the agent is done or dismissed, and when its channel is archived.
4. The micro-VM is Apple's containerization, which runs each isolate on the Virtualization framework on a Mac and on Cloud Hypervisor on Linux, behind one guest contract. See [Each isolate a micro-VM](#each-isolate-a-micro-vm).
5. An agent is done when its branch is merged into its plan's branch or its plan is closed, and dismissing is a control of its own that ends an agent for good. See [Teardown](#teardown).
6. On the owner's Mac, sandbox storage is an APFS disk image on the LaCie drive. See [Making an isolate fast and keeping the host lean](#making-an-isolate-fast-and-keeping-the-host-lean).
7. Every channel's agents run in isolates from the start, a one-person channel's included, and a channel can own its branch from the start ([decisions record](../decisions.md#area-17-the-owners-rulings-on-returning-23-november-2026), row 17.55): one branch per approved plan, so a channel holds several over its life (row 17.56).

**What is proposed on top.**

1. Reviewers get isolates of their own and a fresh context. The final review judges the code and its proof, with instructions the host writes from the approved plan.

**Words.** _Isolate_ is the owner's word for one agent's isolated place; the [vocabulary](../../vocabulary.md#runtime) defines a sandbox per channel and has no word for a place per agent. A _micro-VM_ is a small virtual machine with its own kernel, started per isolate. _Teardown_ is removing an isolate and everything in it. _The host_ means Neuve's process outside the sandbox that holds the Records store and runs Neuve's own steps: Neuve's host on a person's device, and the process the decisions call the channel worker in a shared channel. _Member_ means a person in a channel. _Proof_ is the observed evidence a [validation requirement](../../vocabulary.md#responsibility-and-review-flow) asks for. _Final review_ is the review after the [inner development loop](../../vocabulary.md#responsibility-and-review-flow) approves. A chat's _work lane_ is the worktree and branch it works on. Isolate, micro-VM, teardown, host, member, channel, proof and final review have no vocabulary rows; see [Still open](#still-open-for-the-owner).

## What the eighth answer decides

The [2 November ruling on where coding commands run](../decisions.md#area-12-ace-style-pi-transition-28-october-2026), which keeps sign-ins and the Records store out of the sandbox, and the [9 November ruling on shared sessions](../decisions.md#area-12-ace-style-pi-transition-28-october-2026), which puts the whole runtime in a sandbox on the tailnet, hold together. Three things are new:

- The broker, which already answered Git only for the chat's own repository, now also carries model calls and swaps in the key. A loop runs inside without its key inside.
- Neuve's own steps run outside with the store, and read the branch the broker pushes. That is the mechanical guard for taking a branch back: no Neuve step runs Git in an agent's copy.
- Ace's five served tools (asking a question, writing the plan, answering a plan comment, asking for another agent, messaging an agent) change only channel state, and run inside the sandbox as a user no agent runs as.

The ruling also closes two of the owner's earlier options for a shared channel. A placement on each member's own device would run a channel's agents on a member's machine, which both rulings forbid. "Only the host's" is the same placement with one member. What survives of "each members' agents spawning their own sandboxes" is an isolate per agent inside the shared sandbox, whoever started the agent. A channel with one person still runs on that person's device, by the 2 November ruling.

## Why the narrow folders exist, and the principle

On a person's machine today, each agent's work lane is a linked worktree of the owner's repository. Its Git folder is the owner's: the objects, every branch, the hooks, the Git settings and Neuve's store ([`location.ts`](../../packages/records-core/src/location.ts), line 22). Codex's sandbox keeps that folder read only, so a Codex agent cannot commit. Its source gives the reason: a Git folder "could be modified to escalate the privileges of the agent", because hooks and settings run outside the sandbox the next time anyone runs Git (Codex `protocol.rs`, lines 1343–1347, read by the research lane).

The narrow folders open the worktree's index, new objects and the channel's own branches, and nothing else. They let a commit through and keep hooks, settings, `main` and the store shut. An agent can still delete object files and damage any branch's history.

Each of those patches answers the same problem. The agent's place shares a Git folder with things others trust. If the agent has its own clone and nobody else runs Git in it, its hooks and settings run only for the agent itself, so writing them harms only its own copy (inferred).

**The principle, decided by the ninth answer.** An agent owns everything inside its isolate. Only a branch leaves, with its proof. Trust is checked where the branch comes back, by review. What must stay trustworthy (credentials, Neuve's store) is never inside.

The cloud products the ruling followed work this way, as far as their documentation shows. Claude Code on the web gives each session a fresh virtual machine (4 vCPUs, 16 GB) and a fresh clone; Git goes through a proxy that swaps a stand-in for the real token, the agent pushes a branch, and the person opens the pull request. The proxy refuses branch deletion and tag pushes but does not limit which branches a push updates. Codex cloud now runs "each cloud task" in a virtual machine (up to 4 vCPUs, 16 GiB), gives secrets as stand-ins a proxy fills in, and returns a diff or a pull request the person reviews. Neither names its virtual machine technology (read, in their documentation).

## What the ninth answer decides

The owner chose an isolate per agent over one clone per channel with a work lane per agent and the narrow folders inside, and added two requirements: each isolate is a micro-VM, and it is torn down and cleaned up. Its consequences:

- **Nothing shared is left to guard.** An agent may write everything in its own clone, hooks and settings included, because nobody else runs Git in it. The narrow folders are not used in the shared sandbox.
- **Codex's own sandbox is not needed there.** The micro-VM is the boundary, as the cloud products treat their machine. Codex on Linux uses bubblewrap, which often needs privileges a container lacks; inside a micro-VM it is no longer required.
- **One agent reads another's work only through pushed branches.** The inner-loop reviewer fetches the implementer's branch through the broker, into its own clone.
- **The 2 November ruling's sandbox "holds the chat's worktree".** In a shared channel it now holds a micro-VM per agent. The channel's state and Ace's five served tools stay in the sandbox outside every micro-VM (proposed reading).
- **The shared sandbox is a machine, not a container.** A micro-VM needs the hardware's virtualization: a Mac with Apple silicon, or Linux with KVM on bare metal or in a virtual machine that allows nested virtualization. The one container per channel on Cloudflare that the 2 November ruling named cannot hold micro-VMs (inferred: Cloudflare's containers already run in its own micro-VMs, and nested virtualization there is not documented).

**The narrow folders on the device, the coordinator's reading.** The recommendation put to the owner made the narrow folders the stopgap on a person's device, and the owner did not object. So they stay there, letting Codex agents commit now, until a one-person channel's agents also run in isolates of their own. That is now decided: every channel's agents run in isolates from the start (item 7, row 17.55).

## Each isolate a micro-VM

The owner's direction for this design is to keep it simple and functional. An isolate does four things: it keeps an agent off the host machine and inside its scope, it holds the agent's clone, it lets a branch and its proof out, and it is torn down. For now it is not for confining the network: the owner's answer of 24 November is that "The isolate is more about host access and isolation of scope than network, for now at least". Keys still stay outside, with the broker.

**Decided by the tenth answer, as recommended.** Apple's containerization, on whichever machine is the shared sandbox. It runs each container in its own micro-VM, on the Virtualization framework on a Mac and on Cloud Hypervisor with KVM on Linux, behind the same guest contract, so one isolate serves both machines. Both share folders into the VM read only, which is how the repository gets in. Firecracker has no shared folders, so each agent's repository would need a disk image of its own (read, in each project's documentation).

- **The clone** borrows its objects from one mirror per repository on the sandbox machine, shared read only into every micro-VM, so a clone costs only its own commits and checkout. Git warns that a borrowing clone breaks if its source later drops objects, so the mirror never prunes while a clone borrows from it. Run on the owner's Mac, outside any VM: a borrowing clone of this repository took 0.44 s and 588 KB, against 0.81 s and 20 MB for a full copy, and a commit in it wrote only to its own folder.
- **The branch and proof leave** through the broker, which holds the keys and pushes the branch, as it already answers Git only for the chat's own repository. Proof leaves as files the host collects from the micro-VM before teardown.
- **An idle agent stops.** Its micro-VM is saved and stopped, which frees its memory and keeps its disk, and a mention restores it; on a Mac, memory comes back only when the micro-VM stops.

## Making an isolate fast and keeping the host lean

**The owner's questions, 25 November 2026.** Shown that a lane installs and builds everything again before it works, and that this design builds the micro-VMs on the same steps: "How can we ensure: good speed when creating new sessions for each agent to work on; proper teardown to avoid bloating the host machine; sharing resources (local dependency module installs, build caches and so on) to avoid large filesystem operations every time. What is the common design patterns for systems that provision and run these at scale so we can provide the right closure and sandboxing for them without writing large amounts of FS operations?" On the storage below: "maybe the disk image is the way to go, but is it going to be slower because of this? And yes, we can fold it into the isolate design as it is quite directly involved in that task, ensure to add the learnings in that too". Where the storage lives is decided below; the rest is proposed.

**What a lane does today, read in the review-tab-auto-open channel on 25 November.** Ace makes a lane with a plain `git worktree add` from the main checkout ([`external-lanes.ts`](../../packages/channel/src/external-lanes.ts), `buildWorktree`). It installs nothing and fetches nothing. The implementer then did it in its own shell before working: `bun install` (1.6 GB in `node_modules`), `git submodule update --init` for Neuve Graph (about 22 MB fetched, 343 MB on disk once checked out and built), and `bun run check:graph`, which builds the graph engine, since `bun run check` needs it. About 1.9 GB on disk and several minutes per lane, every lane, and only if the agent remembers. The lanes sat on the Mac's internal disk, over 80% full, though the owner's lane instruction keeps work on the LaCie drive. A micro-VM built the same way would repeat all of it inside every isolate.

**The pattern, proposed.** Systems that start many short-lived sandboxes share one shape: build what is common once, give each sandbox a copy-on-write fork of it, and keep everything the sandbox writes in a layer of its own. Starting a sandbox then points at existing data instead of copying it, and teardown of a sandbox's disk deletes one file instead of walking a tree. This design already does it for Git, with the mirror and the borrowing clone. Applied to the rest:

- **Built once per key, read only.** The toolchain, the installed dependencies and the graph engine's build go into one micro-VM disk, named by what determines it: the lockfile's hash, the Neuve Graph submodule's commit and the toolchain's version. Building it runs the repository's code (install scripts, `go build`), and Neuve's own processes run none of it ([12.28](../decisions.md#area-12-ace-style-pi-transition-28-october-2026)), so the build runs in a micro-VM of its own that the host starts and no agent works in. A second request for the same key waits for the first build and uses it, by the [shared-work record](../../architecture/decisions/0016-shared-work.md).
- **A fork per isolate.** An agent's micro-VM starts from a copy-on-write clone of that disk, plus its borrowing clone of the repository. Its own writes land only in its clone and its fork. Hypeman, the lifecycle reference, forks a new instance from a snapshot this way, cloning the guest's disks with `FICLONE` on Linux file systems that support it and with `clonefile` on macOS, which its note calls "an instantaneous, copy-on-write, space-shared operation" (built in `lib/forkvm/copy_reflink_darwin.go`; a byte copy remains only where the volume cannot clone). Hypeman also restores a VM from standby in milliseconds, which is this design's idle agent saved and stopped.
- **Shared caches mounted read only.** The package store and Go's module cache reach every micro-VM as shared folders, as the mirror does, and only the build's own micro-VM writes them.
- **Teardown by construction.** Since everything an agent wrote is in its own fork and clone, teardown deletes those, and the shared parts stay. A disk built for a key goes once a newer key replaces it and no isolate uses it, so no limit on agents is added. When the current disk and the caches are trimmed is not yet designed.

**The storage this needs, measured on the owner's Mac on 25 November.** Copy-on-write needs APFS. The LaCie drive is HFS+ (journaled), which cannot clone a file, so every fork there would be a full copy, and a clone cannot cross from one volume to another. Three ways: an APFS disk image stored on the LaCie drive, which leaves the drive as it is; converting the drive's volume to APFS in place with `diskutil apfs convert`, which its manual describes as non-destructive for an HFS volume (not tried); or reformatting the drive as APFS, which erases it. The owner chose the disk image: "seems like apfs is the winner design", then "apfs image that is" ([decisions record](../decisions.md#area-17-the-owners-rulings-on-returning-23-november-2026), row 17.53). One run of each, with the main checkout's `node_modules` (1.6 GB, 83,545 files) and a 40 GB APFS sparse bundle on the LaCie drive:

| Operation                                               | Plain LaCie (HFS+)     | APFS image on LaCie             |
| ------------------------------------------------------- | ---------------------- | ------------------------------- |
| Copy all of it in                                       | 24.9 s                 | 25.3 s                          |
| Make one more agent's copy with `cp -c`, file by file   | 24.9 s, a full copy    | 9.4 s                           |
| The same as one `clonefile` call on the folder          |                        | 1.0 s                           |
| Clone a 4 GB disk file, the shape of a micro-VM's disk  | a full copy, not timed | under 1 ms                      |
| Read every file                                         | 33.8 s                 | 40.2 s                          |
| Delete one copy                                         | 4.4 s                  | 4.1 s (a disk file: under 1 ms) |

So the image is not slower to fill. A micro-VM's disk clones at once, which is the case isolates need. A folder of many files clones about 2.6 times faster than a copy file by file, the way Apple supports; one `clonefile` call on the whole folder was about 25 times faster, but Apple's manual "strongly" discourages cloning folders that way. Reading many small files took about a fifth longer, the price of the image layer. A clone took no more space until written: the image held 1.8 GB for the original and a full clone.

**The same pattern before micro-VMs, proposed.** Today's lanes would gain the same way. Ace keeps the lanes folder in the APFS image, together with one installed copy of the dependencies and the engine's build per key, filled once; when it makes a lane it clones those into it and points the Neuve Graph submodule at the main checkout's objects, so the implementer starts in a lane that is ready.

**Not verified.** Each figure above is one run, not repeated. Nothing ran inside a micro-VM. Whether Apple's containerization clones its disks with `clonefile` or copies them, how fast a micro-VM reads a shared folder, and whether a busy image with many isolates keeps these figures, are not known. Whether space freed inside the sparse bundle returns to the LaCie drive without compacting the image is not known.

## Teardown

**Decided.** When an agent is done or dismissed, and when its channel is archived, its isolate, clone and scratch are removed. This carries the owner's [23 November ruling](../decisions.md#area-17-the-owners-rulings-on-returning-23-november-2026) into Ace itself: lanes dispose of what they make, and archiving a channel in Ace disposes of what the channel made. None of T3 Code, opencode or Ace removes a worktree when a thread or channel is archived (read, in their source).

**What it keeps, the coordinator's reading.** Only the branch the broker pushed and the proof that left with it, recorded in the store. Anything the agent did not commit and push is gone, which is the principle that only a branch and its proof leave.

**Decided by the tenth answer, as recommended.**

| Trigger                 | What it is                                                                                                                                                                                                      | What happens                                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| The agent is done       | The work it was started for has ended: its branch is merged into its plan's branch, or the plan it worked on is closed. Not the end of a turn, and not Stop, since a stopped agent starts again on a mention | The host collects its proof, the broker pushes its branch, then the micro-VM, clone and scratch are removed     |
| The agent is dismissed  | A person ends the agent for good. Ace has Stop, which a mention undoes, and nothing that ends an agent for good today, so dismissing needs a control of its own on the agent's line                             | The same, at once                                                                                               |
| The channel is archived | Archiving the channel                                                                                                                                                                                           | Every isolate of the channel is torn down the same way, and its mirror is removed once no clone borrows from it |

- **One teardown per isolate.** When two triggers meet, the teardown runs once and the other caller waits for it, by the [shared-work record](../../architecture/decisions/0016-shared-work.md).
- **Nothing left behind.** Teardown removes the micro-VM with its disk, the clone, the scratch and any volume. When the sandbox machine starts, the host removes every isolate whose agent or channel no longer exists, which is cleanup after a crash, not a limit on agents.

## The final review and the inner-loop reviewer

Two reviewers read a shared channel's work, and the ruling places them differently.

- **The inner-loop reviewer** is an agent of the channel, so it runs inside the sandbox. The [planning design](planning-mode.md#after-approval-what-agents-may-do-and-what-code-still-guarantees) starts it in a new chat with a brief the host writes from the approved plan. Its guidance has it plant a problem and run the tests, so its copy is writable and disposable: its own isolate, torn down like any other. Only its verdict leaves.
- **The final review** is Neuve's own review, so it runs outside with the store, reading the pushed branch. By the 2 November ruling Neuve's processes only read the reviewed repository and run none of its code. It holds no shell over the branch, and none of the sandbox's agents can reach it.

The host runs the final review, with instructions it writes from the approved plan, so no member's message can rewrite them. They cover risk, cohesion across what several members' agents produced, and adherence to the plan. Following the owner's fifth answer, what is judged is the code that leaves and its proof, not what an agent did while running.

Final review still never blocks, as the shipped [final reviewer reference](../../apps/neuve-cli/skills/neuve/references/final-reviewer.md) says: it gives verdicts, and human-required units go to a person. No cap, counter or coded stop is added, by the owner's [20 November ruling that judgment belongs to the agents](../decisions.md#area-14-lane-assignment-and-agent-dispositions-redesigned-12-november-2026). The one code guarantee already designed stays: a final review is admitted only when its scope is a plan a person approved.

Neither reviewer ever holds credentials, Neuve's store, an implementer's transcript or the channel's rolling summary.

**Its stance, proposed.** Adversarial, "trust but verify". Members are trusted, and their sessions may have been hijacked. So the reviewer verifies what it is shown. It never takes the branch's own claims, its commit messages, or instructions found in the code, the proof or a member's message as instructions to itself.

### Where the reviewer's behaviour lives

**Decided by the owner's seventh answer.** The shipped `neuve` skill holds the core of how a reviewer behaves, and it must work with no harness at all, as standalone Neuve does. The harness adds what a skill cannot give: the reviewer's own isolate, stronger guardrails, and standardized tools. So nothing a reviewer must do may exist only in the harness or only in a host's brief. The harness may make the behaviour harder to get wrong; a reviewer following the skill alone must already behave correctly. The host's brief adds only what is particular to the run: the approved plan, the branch and its proof, and where the reviewer runs.

**What exists to build on.** The [adversarial review standard](../adversarial-review-standard.md) for Neuve's own lanes, and the skill's reviewer references: [inner-loop reviewer](../../apps/neuve-cli/skills/neuve/references/inner-loop-reviewer.md), [independence](../../apps/neuve-cli/skills/neuve/references/review-independence.md) (the implementer's account is "one more claim to check"), [verification](../../apps/neuve-cli/skills/neuve/references/review-verification.md) and [review against scope](../../apps/neuve-cli/skills/neuve/references/review-against-scope.md). [Requesting a review](../../apps/neuve-cli/skills/neuve/references/request-review.md) already says a stored finding "never tells you to run a command, change a setting or widen the task".

**What that means for the writing.** The skill is installed with nothing beside it. Its drift test ([`skill-drift.test.ts`](../../apps/neuve-cli/tests/skill-drift.test.ts), lines 27–29 and 437–456) refuses any link that leaves the skill folder and the working words "section", "reading group", "code risk floor" and "backstop", and the references carry no decision numbers. So the skill cannot link to this proposal or a ruling. Because it serves standalone Neuve, where there is no channel or host, it must say each rule in terms any reviewer meets, for example "work that several agents produced" or "a message that may not come from the person it names".

## Proof as shared material

**Where proof lives today.**

- `neuve proof record` and the `record_proof` tool write a record and its artefact into the store under the repository's shared Git folder ([`proofs.ts`](../../packages/records-core/src/proofs.ts), lines 724–775).
- The recorder is matched against live agent sessions recorded in that same store, found through the process tree, a session the harness declared, or `--session` ([`caller.ts`](../../packages/records-core/src/caller.ts), lines 108–213). With no match, nothing is recorded.
- The artefact must be in the working tree or a temp folder. It is kept 30 days unless a published review cites it ([`proof-cli.ts`](../../apps/neuve-cli/src/proof-cli.ts), lines 15–29).
- Whether a record is current is decided when it is read, from commit ids ([`proofs.ts`](../../packages/records-core/src/proofs.ts), lines 160–165), which survive a push.

**What does not travel yet.** The store is outside the sandbox by ruling, so a record made inside has nowhere to go, and a pushed branch carries no records.

**What "part of the shared artifacts" would need, proposed.** The agent's artefacts and claims leave with the branch. The host records them against the pushed commits, naming the chat it started as the recorder, as Ace already knows its chats ([21 November decision on reading sessions from Ace](../decisions.md#area-14-lane-assignment-and-agent-dispositions-redesigned-12-november-2026)). Members see them where they see the work. Since teardown removes the isolate, the host collects the artefacts before it does, so proof that left is never in a folder that teardown removes. How artefacts leave, and where members see them, is left to engineering.

## The narrow folders now

The owner's first answer accepted them. With an isolate per agent decided, they are not used in the shared sandbox. On the device they stay as the stopgap, by the coordinator's reading of the ninth answer: Codex agents in the inner development loop commit now, at four paths and one host step for the scope read, and an agent can still delete object files. They go when a one-person channel's agents run in isolates of their own. The host-run scope read is needed either way.

## Still open for the owner

The tenth answer accepted what was recommended: which micro-VM, and what counts as done with what dismissing is. It covers only those; the points below had no recommendation, or were not put.

- **Which machine is the shared sandbox.** A micro-VM needs a Mac with Apple silicon or Linux with KVM, not a container. Whether it is the owner's Mac on the tailnet for now, and how many agents one machine holds, is the owner's call. No recommendation was made.
- **Whose account a shared channel's turns run on.** The ruling keeps every key out of the sandbox; whose key the broker swaps in is still the open question of the 9 November ruling. The return session's research suggested the member who approved the plan, but this proposal made no recommendation.
- **Whose name authors an unattended agent's commit.** The member who started the work, the one who approved the plan, or the bot account the owner plans ([23 November](../decisions.md#area-15-an-overnight-round-with-the-owner-away-23-november-2026)). No recommendation was made.
- **Which branches the broker may push.** Only the channel's own, or any. Claude Code's proxy leaves this to branch protection. No recommendation was made.
- **What the final review's "own isolate" means**, now that the ruling places reviews outside with the store. This proposal reads it as a fresh context, the pushed branch read only and no shell over it. Whether the review's model reads also run in a process apart from the worker that writes records is the owner's call. Not put in the tenth question.
- **The reviewer's safeguards, guidelines and guardrails.** The point was put without a recommendation, so their content is still theirs to approve. Where they live is decided: in the skill.
- **Vocabulary.** Isolate, micro-VM, teardown, dismissing an agent, host, member, channel, proof and final review have no rows, and need the owner's explicit approval. The sandbox row places a shared channel's sandbox "in the cloud", where the 9 November ruling and the owner's third answer place it on the tailnet, and says it "holds the chat's worktree", where a shared one now holds a micro-VM per agent.
